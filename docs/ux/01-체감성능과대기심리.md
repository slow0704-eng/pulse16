# PULSE·16 — 체감 성능과 대기 심리

UX 리서치 보고서 · 2026-08-08
대상: 배포본 <https://slow0704-eng.github.io/pulse16/> (→ `pulse16-mk16.html`)
방법: Playwright 로 실제 조작 + `performance` API · AudioContext 시계 실측
코드는 한 줄도 고치지 않았습니다. 이 문서만 씁니다.

## 측정 환경과 정직 원칙

| 항목 | 값 |
|---|---|
| 브라우저 | Chromium (Playwright, headless) |
| 뷰포트 | 1440×900 기본 · 1920×1080 · 1366×768 · 768×1024 · 390×844 별도 측정 |
| 오디오 | `sampleRate` 48000 Hz · `baseLatency` 10 ms · `outputLatency` 미보고(headless) |
| 네트워크 | ① 캐시 비움 무제한 ② 캐시 비움 + Slow 4G 에뮬레이션(RTT 150 ms / 1.6 Mbps) |

**이 문서에 «느리다» 고 쓴 것은 전부 실측치가 붙어 있습니다.** 재지 못한 것은
「미측정」 또는 「코드에서 유도」 라고 명시했습니다. 특히 다음 두 가지를 구분합니다.

- **실측**: 시계로 잰 ms. 여러 번 잰 것은 표본을 다 적었습니다.
- **유도**: 코드의 상수(예: `Tone.Transport.start('+0.05')`)와 실측 상수(BPM,
  `baseLatency`)로 계산한 값. 「유도」 표시를 붙였습니다.

측정에 실패한 것도 적어 둡니다. Slow 4G 로 킷 로딩을 처음 재려 했을 때 브라우저
HTTP 캐시가 남아 있어 무의미한 값(202 ms)이 나왔습니다. 캐시를 비우고 다시 재서
1649 ms 를 얻었고, **본문에는 다시 잰 값만 실었습니다.**

# 1. 첫 방문 시나리오 — 초 단위 기술

「음악을 몰라도 틀어 놓으면 곡이 된다」 는 목표를 아는 사람은 만든 팀뿐입니다.
아무 설명 없이 처음 열었을 때 실제로 무슨 일이 일어나는지 초 단위로 적습니다.

## 1-A. 데스크톱(1440×900) · 캐시 없음 · 빠른 회선

| 시각 | 내부에서 벌어지는 일 | 사용자가 보는 것 / 듣는 것 |
|---|---|---|
| 0 ms | `index.html` 요청 (16 ms 에 응답) | 빈 화면 |
| 0–99 ms | Tone.js 를 cdnjs 에서 받음 (66.7 KB, 67 ms) · 자체 파일 44개 139 KB 는 78 ms 에 끝 | 빈 화면 |
| **224 ms** | **First Contentful Paint** | 어두운 판에 `PULSE·16` 이 나타남 |
| 99–283 ms | 동기 스크립트 실행 ≈ **184 ms** — 프리셋 357종 조립 + DOM 5,335개(옵션 3,704개) 생성 | 화면 정지 (이 구간엔 이미 글자가 있어 «멈춤» 으로 느껴지지 않음) |

**331 ms 시점에 사용자가 보는 것을 위에서 아래로 그대로 적으면:**

1. `PULSE·16  MK XVI  VERIFIED PRESETS` · 상태 글자 `Tone.js 준비됨`

5. `KIT 일괄 적용` / `BANK` / `SAMPLE TRIM` / `LOOP DECK` / `직접 URL` (샘플 뱅크)

즉 **처음 열었을 때 이 물건이 «스텝 시퀀서» 라는 단서가 화면에 하나도 없습니다.**

## 1-B. 소리를 내기까지 몇 번을 눌러야 하는가 — 실측

세 갈래를 각각 새 세션(localStorage 비움)에서 실제 클릭으로 확인했습니다.

| 경로 | 클릭 수 | 결과 |
|---|---|---|
| `PLAY` 를 누른다 | **1회** | 소리 남 (실측: `ctx.state` `suspended`→`running`, 라벨 `Play`→`Stop`) |
| 스텝 패드를 누른다 | **1회** | 소리 남 — 패드가 스스로 `wake()` 를 부름 (실측: `ctx.state` `running`, `dataset.v` 0→1, `aria-pressed` false→true) |
| **장르 칩을 누른다** | **몇 번을 눌러도 소리 안 남** | 실측: 클릭 후 600 ms 대기해도 `ctx.state`=`suspended`, `Transport`=`stopped`, `ctxTime` 0 그대로. 바뀌는 것은 BPM 숫자(88→134) 뿐 |

**최소 클릭 수는 1회입니다. 문제는 그 1회가 어느 버튼인지 화면이 말해 주지 않는 것입니다.**
화면에서 가장 크고 가장 많고 가장 눌러 보고 싶은 것은 장르 칩 357개인데,
그것이 유일하게 **소리를 내지 못하는 컨트롤**입니다.

칩 클릭 핸들러(`src/ui/build.js` 의 `b.onclick`)에는 `wake()` 호출이 없습니다.
`restartSong()` 은 `if(playing)` 안에서만 트랜스포트를 만지므로, 정지 상태에서
장르를 바꾸면 상태만 조용히 갈아치우고 끝납니다.

## 1-D. PLAY 를 누른 순간 — 실측

`PLAY` 첫 클릭은 세 가지가 한꺼번에 일어납니다. `start()` → `wake()` → `boot()` →
`Tone.start()` → `Tone.Transport.start('+0.05')`.

| 구간 | 실측 |
|---|---|
| `pointerdown` → 클릭 핸들러 반환 (메인 스레드 정지) | **134.6 / 157.7 / 159.1 / 163.6 / 184.2 ms** (5회) |
| 그중 `boot()` 가 차지하는 시간 | **133.5 / 133.6 / 156.3 / 157.8 / 162.0 / 182.6 / 188.9 / 191.3 / 293.1 ms** (9회) — 중앙값 **162 ms**, 최소 133.5, 최대 293.1 |
| `Tone.Transport` 가 실제로 돌기 시작하는 시각 (오디오 시계) | 클릭 후 **+50.0 ms · +50.7 ms** (2회) |
| 스피커까지 (`baseLatency` 10 ms 더함) | **유도: 약 60 ms** |
| **클릭 → 첫 드럼 소리 (첫 클릭)** | **유도: 195 ~ 355 ms** (boot 133~293 + 50 + 10) |
| **클릭 → 첫 드럼 소리 (두 번째 이후)** | **실측+유도: 약 60 ms** |

`boot()` 안에서 **AudioNode 495개**를 한 번에 만듭니다(실측, `createXxx` 호출 계수):

| 노드 | 개수 |
|---|---|
| `createGain` | 230 |
| `createBiquadFilter` | 149 |
| `createOscillator` | 40 |
| `createWaveShaper` | 23 |
| `createStereoPanner` | 23 |
| `createBuffer` | 7 |
| `createChannelMerger` | 6 |
| `createDelay` | 5 |
| `createAnalyser` | 5 |
| `createBufferSource` | 4 |
| `createDynamicsCompressor` | 2 |
| `createConvolver` | 1 |
| **합계** | **495** |

이 중 무거운 것은 노드 개수가 아니라 **자바스크립트 루프로 굽는 버퍼**입니다.
`graph.js` 안에서 클릭 한 번에 동기로 다 굽습니다.

- 화이트 노이즈: 4초 × 48 kHz = **192,000 샘플** (`Math.random()` 루프)
- 핑크 노이즈: 192,000 샘플 × **7탭 IIR** (Paul Kellett) — 표본당 곱셈 7회 + 덧셈 7회
- 임펄스 응답 3종: `makeIR(0.9…)` `makeIR(1.7…)` `makeIR(3.0…)` — 합 5.6초 분량, **약 268,800 샘플**
- 왜이브셰이퍼 커브: `mkCurve` 4종 + `mkTube` 7종 + `mkCeiling` 1종

합계 **65만 샘플 이상**을 사용자가 PLAY 를 누른 뒤에 굽습니다.

# 2. 대기 지점 목록 — 실측 · 진행 표시 · 심리학 판정

Nielsen 의 세 경계와 Doherty 임계를 기준선으로 씁니다.

- **0.1 초** — 시스템이 «즉시» 반응한 것으로 느낌. 직접 조작감이 유지되는 한계
- **1 초** — 생각의 흐름은 유지되나 «기계가 일한다» 는 것을 알아챔. 지연 표시 필요
- **10 초** — 주의 유지 한계. 확정형 진행 표시와 빠져나갈 길이 필수
- **Doherty 400 ms** — 이 아래로 내려가면 사용자 생산성이 급격히 오르는 경제적 임계

## 2-0. 악기에는 Doherty 400 ms 로는 부족합니다 — 판정

**「이 도구는 악기이므로 더 엄격해야 하는가?」 — 그렇습니다. 다만 조작을 두 종류로 갈라야 합니다.**

Doherty 400 ms 는 «질의 → 응답» 형 업무 도구의 경제적 임계입니다. 악기에는
그보다 훨씬 좁은 다른 기준이 걸립니다. **동작–소리 지연(action-to-sound latency)** 은
운동 감각과 청각을 하나의 사건으로 묶는 문제이고, 그 통합 창은 수십 ms 규모입니다.
대략 10 ms 아래는 프로 연주 기준, 20~30 ms 는 «칠 수 있다», 50 ms 를 넘으면
연주자가 «악기가 나에게서 떨어져 있다» 고 보고하며, 100 ms 를 넘으면 내 손이
소리를 냈다는 인과 자체가 흐려집니다.

그래서 PULSE·16 의 조작을 두 등급으로 나눠 판정합니다.

- **연주 조작(악기 등급, 목표 ≤ 30 ms)** — 스텝 패드, 음색 셀렉트, 볼륨/튠 노브.
  내가 지금 만든 소리를 그 자리에서 들어야 하는 것들.
- **편성 조작(도구 등급, 목표 ≤ 400 ms)** — PLAY, 장르 칩, 뱅크 전환, 킷 로딩.
  «곡을 바꾼다» 는 뜻이므로 한 박자 정도의 지연은 오히려 자연스러움.

이 잣대로 재면 PULSE·16 은 **연주 조작은 훌륭하고, 편성 조작 중 첫 PLAY 와
샘플 로딩 두 곳만 문제**입니다. 아래에서 하나씩 봅니다.

## 2-2. 능동적 대기 vs 수동적 대기 — 판정

대기 심리의 핵심은 «얼마나 기다렸나» 가 아니라 «기다리는 동안 할 일이 있었나» 입니다.
같은 시간이라도 수동적 대기는 능동적 대기보다 훨씬 길게 느껴집니다.

PULSE·16 을 이 잣대로 훑으면 **의외로 좋은 구조**를 이미 갖고 있습니다.

| 대기 | 종류 | 근거 |
|---|---|---|
| 페이지 로드 | **수동적** | 331 ms 라 문제 아님. 단 Slow 4G 1648 ms 는 빈 화면 응시 = 순수 수동 |
| **PLAY 첫 클릭 133~293 ms** | **수동적 · 게다가 메인 스레드가 멈춤** | 이 구간에 사용자는 아무것도 못 함. 클릭도 스크롤도 안 먹음. 「눌렀는데 먹었나?」 구간 |
| 킷 일괄 적용 976 ms | **능동적으로 만들 수 있는데 안 하고 있음** | 합성 엔진이 이미 돌고 있으므로 **음악은 계속 나는 상태**. 즉 사용자는 «듣고 있으면서» 기다릴 수 있는데, 화면이 그 사실을 말해 주지 않아 수동적 대기로 느껴짐 |
| `전체 받기` 2738 ms | **능동적** ✅ | 버튼만 disabled 되고 나머지 UI 는 다 살아 있음. 재생하며 딴 걸 만질 수 있고, 카운터가 진척을 보여 줌. **모범 사례** |
| Loop Deck 691 ms | **수동적 · 무표시** | 눌렀는데 화면·소리 어느 쪽에도 변화가 없어 «안 눌렸다» 로 해석됨 |

**결론: 이 앱의 최대 자산은 «합성 엔진만으로 전 기능이 돈다» 는 것입니다.**
즉 **모든 네트워크 대기가 원리적으로 능동적 대기가 될 수 있습니다** — 음악은 이미
나고 있고, 샘플은 «더 좋아지는 것» 일 뿐이니까요. 그런데 지금 UI 는 그것을
`합성 엔진 사용 중 — 샘플은 필요할 때만 내려받습니다` 라는 한 줄로만 알려 주고,
로딩이 시작되면 그 글자를 `킷 적용 중…` 으로 **덮어써 버립니다**. 안심을 주던
문장을 지우고 불확실성으로 바꾸는 셈입니다.

## 2-3. 불확실성 — 진행 표시 없는 대기의 지도

불확실한 대기는 확실한 대기보다 길게 느껴집니다. 「얼마나 남았는지 모르는 것」이
그 자체로 비용입니다. 진행 표시 유무로 정리하면:

| 진행 표시 | 대기 지점 |
|---|---|
| ✅ 확정형 (n/총계) | `전체 받기` (`12/70 · 실패 0`, 4개마다, 20회 갱신) |
| ⚠ 비확정형 («하는 중» 글자 1회) | 킷 일괄 적용(743~1456 ms 무변화) · 피아노 샘플러 · 직접 URL |
| 🔴 **전무** | **PLAY 첫 클릭의 boot 133~293 ms** · **Loop Deck 691 ms** |

특히 **PLAY 첫 클릭**은 진행 표시가 없는 것보다 나쁩니다. 메인 스레드가 133~293 ms
멈추므로 **버튼의 `:active` 상태조차 다시 그려지지 않을 수 있습니다.** 사용자 입장에선
「눌렀는데 아무 반응이 없다 → 한 번 더 누른다」 가 자연스러운 반응이고, 두 번 누르면
`playing ? stop() : start()` 이므로 **재생이 곧바로 멈춥니다.** 즉 이 구간의 불확실성은
「기분이 나쁘다」 로 끝나지 않고 **기능 실패로 이어집니다.**

## 2-4. 조작 → 결과의 인과 — 판정

악기는 즉각적 피드백이 신뢰를 만듭니다. 인과가 보이는지 하나씩 봤습니다.

| 조작 | 시각 피드백 | 청각 피드백 | 인과 판정 |
|---|---|---|---|
| 스텝 패드 | ✅ 동기 (`dataset.v` 0→1, `aria-pressed` true) | ✅ **즉시 소리** (`+0.02`) | ✅ **완벽.** 내가 켠 스텝이 곧바로 울림 |
| 음색 셀렉트 | ✅ 셀렉트 값 | ✅ `audition()` 즉시 소리 | ✅ **완벽** |
| PLAY (2회차 이후) | ✅ 라벨 `Play`↔`Stop` 동기 · 헤드 표시 점등 | ✅ 약 60 ms | ✅ 양호 |
| **PLAY (첫 클릭)** | ⚠ 라벨은 바뀌지만 **133~293 ms 뒤에야 화면에 반영** | ⚠ 195~355 ms | 🔴 **인과가 끊김** |
| **장르 칩 (정지 상태)** | ⚠ 칩 하이라이트 + BPM 숫자만 | 🔴 **소리 없음** | 🔴 **인과 없음.** 357개 중 하나를 눌렀는데 «뭔가 골라진 것 같긴 한데 아무 일도 없다» |
| 장르 칩 (재생 중) | ✅ 칩 하이라이트 · BPM · 스텝 그리드 갱신 | ✅ 즉시 — `restartSong()` 이 `Tone.Transport.position=0` 으로 되돌리고 선율·리프·진행·그루브를 그 자리에서 새로 뽑음 (`sequencer.js:550-580`). **유도: 다음 16분음표(88 BPM 에서 170 ms) 안 + lookAhead 80 ms** | ✅ **훌륭.** 곡이 새 장르의 «1» 부터 다시 시작하는 것이 귀에 또렷이 들림 |
| **Loop Deck 버튼** | 🔴 클릭 직후 아무 변화 없음(실측: `dataset.on` 0 유지, `kstat` 불변) | 691 ms 뒤 소리 | 🔴 **인과 없음** |
| 킷 일괄 적용 | ⚠ `킷 적용 중…` 글자만 | 976 ms 뒤 음색이 바뀜 | ⚠ 약함 |

## 2-5. 대기가 아니지만 첫 인상을 깎는 것들 (실측)

측정 중에 발견한, 지연은 아니지만 «이 물건을 믿을 수 있나» 에 직결되는 것들입니다.
지연 개선과 별개로 첫 인상 비용이 크므로 적어 둡니다.

1. **머리글의 숫자가 서로 안 맞습니다.** 첫 화면에 `PATTERN LIBRARY — 208종 · 208종 표시`
   와 `전체 357` 이 **나란히** 보입니다. 실측: 배포본에 `#libtotal` 요소가 **없어서**
   (`getElementById('libtotal')` → `null`) `build.js` 의 갱신 코드가 아무 일도 못 하고,
   HTML 에 박힌 옛 숫자 208 이 남습니다. 칩 개수는 실제로 357개(`.chip` 357, 표시 357).
   → 처음 보는 사람이 가장 먼저 읽는 줄에서 숫자가 어긋납니다.
2. **Loop Deck 7개 중 3개가 404 입니다.** 실측 응답 코드:
   `ominous` 200 · **`chorus` 404** · **`drums` 404** · **`breakbeat` 404** ·
   `handdrum` 200 · `conga` 200 · `theremin` 200.
   404 난 버튼은 `dataset.dead='1'` 로 **영구히 죽고**, 그 뒤로는 눌러도 아무 일도 안 합니다.
3. **404 가 사용자에게 거짓 진단을 보여 줍니다.** `blocked()` 가 띄우는 경고 배너는
   > 외부 샘플(tonejs.github.io)에 접근하지 못했습니다. **이 미리보기 창이 외부 오디오
   > 요청을 차단했을 가능성이 큽니다.** 파일을 내려받아 브라우저에서 직접 열면 모두
   > 정상 동작하며, …

   실제 원인은 그냥 **파일이 없는 것(404)** 입니다. 사용자는 자기 브라우저나 환경을
   의심하게 되고, 「파일을 내려받아 직접 열라」 는 헛수고를 권유받습니다.
   잘못된 원인 귀속은 대기 불만보다 신뢰를 더 크게 깎습니다.
4. **HELP 는 이 물건이 무엇인지 설명하지 않습니다.** 실측: 전체 **225자**, 내용은
   단축키 목록(Space·1~4·Ctrl+Z·드래그·?·Esc)뿐. 「무엇을 하는 물건인지」
   「어디를 눌러야 소리가 나는지」 는 한 글자도 없습니다. 게다가 y 731 px 의
   작은 `?` 버튼 뒤에 숨어 있어 처음 온 사람이 열어 볼 이유가 없습니다.

# 3. 고치는 방법 — 「체감」 과 「실제 지연」 을 구분해서

여기서 두 가지를 엄격히 갈라 씁니다.

- **[체감]** 실제 ms 는 그대로 두고, 느껴지는 시간만 줄이는 것
- **[실측]** 실제 ms 자체를 줄이는 것

각 항목마다 **트레이드오프**와 **어느 쪽이 이 제품에 맞는지 결론**을 붙입니다.

## 3-A. PLAY 첫 클릭의 boot 133~293 ms 🔴 최우선

### [실측] 방법 1 — 굽기를 미리 한다 (프리베이크)

`boot()` 의 무게는 노드 495개가 아니라 **65만 샘플 굽기**입니다. 이것을 페이지
로드 직후 유휴 시간으로 옮깁니다. AudioContext 없이 `Float32Array` 로만 미리 계산해
두고, `boot()` 은 그것을 `AudioBuffer` 에 복사만 합니다.

> **트레이드오프:** 「미리 다 구우면 첫 로딩이 길어진다」 — 맞습니다. 다만 지금
> 로드가 331 ms 로 여유가 크고, `requestIdleCallback` 으로 넣으면 **FCP 224 ms 와
> `domInteractive` 283 ms 에는 영향이 없습니다.** 첫 화면이 뜬 뒤의 유휴 시간을
> 쓰는 것이므로 「첫 로딩이 길어진다」 는 대가를 사실상 치르지 않습니다.
>
> **결론: 이 제품에 맞습니다. 채택.** 사용자가 첫 화면을 읽고 PLAY 를 찾아
> 마우스를 옮기는 데 최소 1~2초가 걸립니다. 그 시간은 지금 100% 낭비되고 있고,
> 굽기(65만 샘플, 실측 130~290 ms)를 다 넣고도 남습니다.

### [실측] 방법 2 — 첫 소리에 필요 없는 것을 뒤로 미룬다 (지연 굽기)

`boot()` 이 만드는 것 중 **첫 드럼 한 방에 필요한 것은 일부뿐**입니다.
`ampIn.body_banjo` / `body_sitar` / `amp_fuzz` / `bass_upright` 같은 기타·베이스
몸통 체인(biquad 149개의 큰 몫)과 모달 뱅크는 **그 엔진을 쓰는 프리셋을 고를 때까지
아무 일도 하지 않습니다.** 기본 프리셋은 Boom Bap 입니다.

> **트레이드오프:** 「지연 로딩하면 첫 조작이 끊긴다」 — 이것이 진짜 위험입니다.
> 재생 중에 기타 엔진이 필요해진 순간 그 체인을 만들면, **오디오 스레드가 도는
> 중에 메인 스레드가 수십 ms 멈추면서 소리가 튑니다.** 재생 중 글리치는 첫 클릭의
> 200 ms 보다 훨씬 나쁜 인상을 줍니다(악기의 신뢰를 직접 깎음).
>
> **결론: 부분 채택 — «지연» 이 아니라 «앞당김» 으로 씁니다.** 첫 소리 경로만
> `boot()` 에 남기고, 나머지는 **PLAY 직후 유휴 시간에 스스로 이어서 굽습니다**
> (필요해질 때가 아니라, 필요해지기 전에). 사용자가 장르 칩을 찾아 고르는 데
> 걸리는 몇 초가 그 예산입니다. 「필요할 때 만들기」 는 채택하지 않습니다.

### [체감] 방법 3 — 낙관적 UI: 먼저 그리고 나중에 굽는다

지금은 `boot()` 이 끝나야 화면이 갱신됩니다(133~293 ms 동안 정지).
순서를 뒤집습니다. 클릭 즉시 라벨을 `Stop` 으로 바꾸고 헤드를 점등한 **다음**,
브라우저가 한 프레임 그리게 양보하고, 그 뒤에 `boot()` 을 돌립니다.

> **트레이드오프:** 실제 소리는 여전히 195~355 ms 뒤에 납니다. 「눌렀다」 는
> 확인은 즉시 오지만 소리와 화면이 어긋나는 구간이 생깁니다.
>
> **결론: 채택. 단독으로는 부족하고 방법 1과 함께 씁니다.** 시각 확인을
> 0 ms 로 당기는 것만으로 **더블클릭 → 즉시 정지** 라는 기능 실패를 막습니다.
> 이것이 이 항목에서 가장 값싼 승리입니다.

### [체감] 방법 4 — 소리로 주는 피드백: 첫 한 방을 먼저 때린다

트랜스포트를 기다리지 않고, `boot()` 직후 **킥 한 방을 즉시** 울립니다
(스텝 패드가 이미 하는 것과 같은 `ctx.currentTime+0.02` 경로). 그 다음에
트랜스포트가 `+50 ms` 에 들어옵니다.

> **트레이드오프:** 킥이 한 번 더 들려 첫 마디가 미묘하게 두꺼워질 수 있습니다.
> 다만 트랜스포트도 스텝 0 에 킥을 치는 프리셋이 기본(Boom Bap: 1박 1번째 켜짐,
> 실측)이므로 **거의 같은 자리에 겹칩니다** — 어색하지 않을 여지가 큽니다.
>
> **결론: 방법 1을 먼저 하고, 그래도 60 ms 아래로 못 내려가면 채택.**
> 방법 1이 성공하면 첫 클릭도 약 60 ms 가 되므로 이 트릭이 불필요해집니다.
> 순서상 뒤에 둡니다.

## 3-B. 킷 일괄 적용 976 ms (Slow 4G 1649 ms) 🔴

### [실측] 방법 1 — 순차 요청을 병렬로 바꾼다

`sampler.js` 의 `applyWholeKit` 은 `for(const t of TRACKS) await assignSample(...)`
로 **7 트랙을 한 줄로 세워** 기다립니다. `KIT_MAP` 때문에 실제 고유 파일은 6개
(실측: `캐시 6개`)이고, 파일 1개 왕복이 실측 198~223 ms 이므로
6 × 약 160 ms ≈ 실측 976 ms 와 맞습니다. 동시에 받으면 **1왕복 ≈ 250 ms** 로 줄어듭니다.

> **트레이드오프:** 동시 요청 6개는 `preloadAll` 이 이미 쓰는 동시성(6워커)과
> 같으므로 새 위험이 아닙니다. 실패 처리만 `Promise.allSettled` 로 바꿔
> 한 파일이 죽어도 나머지가 적용되게 해야 합니다(지금은 `ok` 카운트로 이미 그런 형태).
>
> **결론: 채택. 이 문서에서 노력 대비 효과가 가장 큰 항목입니다.**
> 976 ms → 약 250 ms 는 **1초 경계를 0.1~1초 구간으로 되돌리는** 변화이고,
> 코드 변경은 루프 하나입니다.

### [체감] 방법 2 — 기다리는 동안 할 일을 준다 (능동적 대기로 전환)

지금 `킷 적용 중…` 은 **안심을 주던 문장을 지우고** 그 자리에 불확실성을 넣습니다.
문구를 바꿔 **음악이 계속 난다는 사실을 대기 중에 알려 줍니다.**

- 지금: `CR78 킷 적용 중…` (743 ms 동안 고정)
- 제안: `CR78 받는 중 3/6 — 그동안 합성 엔진으로 계속 연주합니다`

> **트레이드오프:** 없음에 가깝습니다. 글자만 바뀝니다. 유일한 비용은
> 진행 카운터를 위해 완료 콜백을 세는 코드가 조금 늘어나는 것입니다.
>
> **결론: 채택. 방법 1과 같이 넣습니다.** 병렬화로 250 ms 가 되면 진행 표시가
> 거의 안 보이게 되지만, **Slow 4G 에서는 여전히 400 ms 이상**이므로 필요합니다.

### [체감] 방법 3 — 스켈레톤은 쓰지 않습니다

이 대기는 «화면이 채워지기를 기다리는» 종류가 아니라 «소리가 좋아지기를 기다리는»
종류입니다. 스켈레톤(자리 표시 회색 블록)은 시각 콘텐츠 대기용 장치라 여기엔
맞지 않습니다.

> **결론: 기각.** 대신 «지금 합성으로 나고 있음» 을 말하는 3-B 방법 2가 이 자리의
> 스켈레톤 역할을 합니다.

## 3-C. Loop Deck 691 ms · 무표시 🔴

### [체감] 방법 1 — 낙관적 UI + 버튼 자체를 진행 표시로 쓴다

클릭 즉시 `dataset.on='pending'` 으로 바꿔 버튼을 «불이 켜지려는 상태» 로 그립니다
(예: 테두리 펄스). 버퍼가 도착하면 `'1'`, 실패하면 `'dead'`.

> **트레이드오프:** 낙관적 UI 는 실패했을 때 상태를 되돌려야 하고, 되돌림이
> 사용자에게 «거짓말을 했다» 로 보일 수 있습니다. 여기서는 세 상태를 눈에 보이게
> 구분(대기 / 켜짐 / 죽음)하므로 «켜졌다가 꺼지는» 오해가 생기지 않습니다.
>
> **결론: 채택.** 691 ms 를 줄이는 것보다 **눌렸다는 사실을 0 ms 에 알려 주는 것**이
> 훨씬 중요합니다. 실제 지연은 CDN RTT 라 우리가 줄일 수 없습니다.

### [실측] 방법 2 — 404 3개를 고친다

`chorus` · `drums` · `breakbeat` 는 `drum-samples/loops/*.mp3` 를 가리키는데 그
경로에 파일이 없습니다(실측 404). 성공하는 3개는 경로 모양이 다릅니다
(`drum-samples/handdrum-loop.mp3`, `drum-samples/conga-rhythm.mp3`).

> **트레이드오프:** 없음. 데이터 오류입니다.
>
> **결론: 채택.** 다만 이건 지연 문제가 아니라 정확성 문제이므로 소유 팀에 넘깁니다.
> **체감 관점에서 더 중요한 것은 3-E 의 오진단 메시지입니다.**

## 3-D. 장르 칩 357개가 소리를 못 낸다 🔴

### [체감/실측] 방법 1 — 칩 클릭이 재생을 시작하게 한다

칩 핸들러 끝에 «정지 상태면 재생을 시작한다» 를 넣습니다. 스텝 패드가 이미
`wake()` 로 하는 것과 같은 원리이고, 칩은 **곡을 통째로 고르는 조작**이므로
「고르면 들린다」 가 자연스러운 기대입니다.

> **트레이드오프:** 사용자가 «정지한 채로 프리셋만 갈아 두고 싶은» 경우를 빼앗습니다.
> 그리고 소리가 갑자기 나는 것을 놀람으로 받아들일 수 있습니다.
> 반대로, 이 도구의 목표가 «음악을 몰라도 틀어 놓으면 곡이 된다» 라면
> **정지 상태로 프리셋만 고르는 것은 목표 사용자의 행동이 아닙니다.**
> 정지 상태로 편집하고 싶은 사람은 이미 PLAY/Space 를 알고 있는 숙련자입니다.
>
> **결론: 채택. 단, «첫 상호작용일 때만» 으로 한정합니다.** 사용자가 한 번도
> 재생한 적 없으면(=`boot()` 전) 칩 클릭이 재생까지 갑니다. 이미 재생했다가
> 스스로 멈춘 사용자에겐 그 의도를 존중해 재생하지 않습니다. 이렇게 하면
> 첫 방문자의 인과 단절만 없애고 숙련자의 통제권은 지킵니다.

### [체감] 방법 2 — 첫 화면에 «무엇인지» 를 한 줄 넣는다

`VERIFIED PRESETS` 는 만든 사람의 언어입니다. 처음 온 사람에게 필요한 것은
**이 물건이 무엇이고 무엇을 누르면 되는지** 입니다. 이미 있는 `.tagline` 자리를 씁니다.

> **트레이드오프:** 브랜드 톤(절제된 장비 느낌)을 조금 잃습니다. 한 줄이 늘어
> PLAY 가 아래로 밀립니다(모바일에서 이미 첫 화면 밖이라 더 나빠짐).
>
> **결론: 채택하되 «PLAY 를 위로 올리는 것»(3-F)과 반드시 함께 합니다.**
> 설명만 넣고 버튼을 그대로 두면 첫 화면이 더 나빠집니다.

## 3-E. 오진단 경고 배너

### [체감] 잘못된 원인 귀속을 없앤다

`blocked()` 는 모든 로딩 실패를 「미리보기 창이 차단했을 가능성이 큽니다」 로
설명합니다. 실측한 실패 3건은 전부 **404** 였습니다. 사용자에게 자기 환경을
의심시키고 「파일을 내려받아 직접 열라」 는 헛수고를 권합니다.

> **트레이드오프:** 원인별로 문구를 나누려면 실패 사유(404 / 네트워크 / 타임아웃)를
> 구분해 전달해야 하므로 `loadBuf` 의 예외에 정보를 담아야 합니다.
>
> **결론: 채택.** 대기 심리에서 **잘못된 설명은 무설명보다 나쁩니다.** 무설명은
> 불확실성이지만, 오설명은 사용자를 틀린 행동으로 보내고 신뢰를 깎습니다.
> 그리고 **어떤 문구든 마지막에 «지금도 합성 엔진으로 전부 연주됩니다» 를
> 남겨야** 실패가 «막힘» 이 아니라 «옵션 하나 못 받음» 으로 읽힙니다.

## 3-F. 첫 화면 구성 (특히 모바일)

## 3-G. Slow 4G 의 빈 화면 1648 ms

### [체감] 방법 1 — 스켈레톤이 아니라 «브랜드 판» 을 먼저 보낸다

FCP 1648 ms 의 원인은 `<head>` 의 CSS 5개 + cdnjs Tone.js 가 렌더를 막는 것입니다

`<script>` 가 `<head>` 에 있어 파서를 막습니다.

> **트레이드오프:** Tone.js 를 `defer` 로 옮기면 렌더는 빨라지지만 실행 순서가
> 바뀝니다. 이 프로젝트는 **클래식 스크립트의 로드 순서가 곧 의존 순서**이고
> (`main.js` 주석에 명시), `HAS_TONE` 판정이 전역에서 즉시 일어납니다.
> 순서를 잘못 건드리면 앱이 통째로 죽습니다 — 실제로 다른 담당자가 `src/` 전역을
> 동시에 수정 중이라 위험이 큽니다.
>
> **결론: 「Tone.js 를 defer 로」 는 기각.** 위험 대비 이득이 낮습니다.
> 대신 **인라인 CSS 로 브랜드 판 한 조각만 먼저 그립니다** — `<head>` 안에
> 최소 스타일(배경색 + 브랜드 글자)을 인라인으로 두면 CSS 5개와 Tone.js 를
> 기다리지 않고 첫 픽셀이 나갑니다. 이건 순서 의존과 무관합니다.

### [실측] 방법 2 — CSS 5개를 1개로 합친다

`tokens.css` `layout.css` `rack.css` `sequencer.css` `controls.css` 5개가 모두
렌더 블로킹입니다. Slow 4G 에서 RTT 150 ms × 연결 재사용을 고려해도 왕복 비용이 붙습니다.

> **트레이드오프:** 파일을 나눠 둔 것은 여러 담당자가 병렬로 작업하기 위한 구조입니다.
> 합치면 그 협업 이점이 사라집니다.
>
> **결론: 소스는 5개로 유지하고 배포 시에만 합칩니다.** 지금 빌드 단계가 없으므로
> 우선순위는 낮게 둡니다(6절 참조).

# 4. 트레이드오프 총괄 — 이 제품의 결론

과제에서 지목한 대립을 정면으로 답합니다.

> **「미리 다 구우면 첫 로딩이 길어지고, 지연 로딩하면 첫 조작이 끊긴다.
> 어느 쪽이 이 제품에 맞는가?」**

**답: 둘 다 아닙니다. «첫 화면이 뜬 뒤의 유휴 시간에 굽기» 가 이 제품의 정답입니다.**

근거는 실측 세 개입니다.

1. **첫 로딩에 여유가 있습니다.** FCP 224 ms · load 331 ms. 로딩이 짧아서
   프리베이크를 얹을 «빈 시간» 이 로드 *이후* 에 충분히 있습니다.
2. **사용자가 PLAY 를 찾기까지 시간이 걸립니다.** 첫 화면에 357개 칩이 있고
   PLAY 는 628 px 아래(모바일 1098 px)에 있습니다. 읽고 찾고 마우스를 옮기는 데
   최소 1~2초가 갑니다. 굽기 예산(실측 133~293 ms)의 5~10배입니다.
3. **재생 중 굽기는 절대 안 됩니다.** 이 앱은 악기입니다. 재생 중 메인 스레드가
   수십 ms 멈추면 소리가 튀고, 그 한 번이 «못 믿을 악기» 라는 인상을 남깁니다.
   첫 클릭의 200 ms 는 한 번뿐이지만, 재생 중 글리치는 연주 내내 반복됩니다.

따라서 시간축을 이렇게 나눕니다.

| 구간 | 무엇을 하는가 | 근거 |
|---|---|---|
| 0 ~ 331 ms | 지금 그대로. 아무것도 더하지 않음 | FCP 224 ms 를 지켜야 함 |
| **331 ms ~ 첫 클릭** | **유휴 시간에 노이즈·IR·커브를 굽고 첫 소리 경로 노드를 만듦** | 사용자가 화면을 읽는 시간 = 공짜 예산 |
| 첫 클릭 | 라벨을 먼저 바꾸고, 구워 둔 것을 꽂기만 함 | boot 133~293 ms → 목표 60 ms |
| **첫 클릭 이후 유휴** | 나머지 앰프 체인·모달 뱅크를 이어서 굽기 | 장르를 고르기 전에 미리 끝냄 |
| 재생 중 | **아무것도 새로 굽지 않음** | 글리치 금지 |

같은 논리를 샘플에도 적용합니다. **샘플은 «미리 다 받기»(2738 ms) 도 «필요할 때
받기»(976 ms 순차) 도 아니라, «필요할 때 병렬로 받되 그동안 합성으로 계속 연주» 가
맞습니다.** 합성 엔진이 전 기능을 커버한다는 이 앱의 구조가 그것을 가능하게 합니다 —
샘플 대기는 «기능이 막힌 대기» 가 아니라 «더 좋아지기를 기다리는 대기» 이고,
그렇게 **말해 주기만 하면** 능동적 대기가 됩니다.

# 6. 구현 명세 — 어느 파일에 무엇을

다른 팀이 그대로 붙일 수 있게 파일·함수·조건을 적습니다.
**저는 코드를 고치지 않았습니다.** 아래는 제안입니다.
`src/` 전역이 동시 수정 중이므로, 각 항목에 **충돌 위험**을 표시했습니다.

## 6-1. [P0] 장르 칩이 첫 상호작용이면 재생까지 간다

**파일:** `src/ui/build.js` — `LIB_NAMES.forEach(...)` 안의 `b.onclick`
(현재 `restartSong(); syncAll(); markDirty();` 로 끝나는 곳)

**추가 위치:** `markDirty()` 바로 뒤

```
// 아직 한 번도 소리를 낸 적이 없다면, 장르를 고른 것을 «틀어 달라» 로 해석한다.
```

## 6-2. [P1] PLAY 낙관적 UI — 화면을 먼저 그리고 나중에 굽기

**파일:** `src/seq/sequencer.js` — `function start()` (584행)

**현재 순서:** `wake()` → 라벨 변경 → `Transport.start()`
**바꿀 순서:** 라벨 변경 → 한 프레임 양보 → `wake()` → `Transport.start()`

```
function start(){
  /* ① 먼저 «눌렸다» 를 그린다. boot() 가 133~293ms 메인 스레드를 잡으므로
     (docs/ux/01-체감성능과대기심리.md 실측) 순서를 뒤집지 않으면 :active 조차
     다시 그려지지 않고, 사용자가 한 번 더 눌러 곧바로 stop() 이 된다. */
  playing = true; step = 0;
  UI.play.dataset.on='1'; UI.play.textContent='Stop';
  UI.head.classList.add('on');

  /* ② 이미 부팅됐으면 지금 바로 (한 프레임도 늦추지 않는다 — 60ms 경로 유지) */
  if(booted){ startTransport(); return; }

  /* ③ 첫 클릭만: 그린 것을 화면에 내보낸 뒤 굽는다 */
  requestAnimationFrame(() => { requestAnimationFrame(() => {
    wake();
    startTransport();
  });});
}
function startTransport(){
  if(HAS_TONE){ Tone.Transport.position=0; Tone.Transport.start('+0.05'); }
  else{ fbStep=0; fbNext=ctx.currentTime+0.08; fbTimer=setInterval(fbLoop,25);
        requestAnimationFrame(fbPaint); }
}
```

- ⚠ **주의:** `wake()` → `Tone.start()` 는 사용자 제스처 «안» 에서 불려야
  브라우저가 AudioContext resume 을 허용합니다. `requestAnimationFrame` 콜백은
  제스처 컨텍스트를 벗어납니다. **이 방식은 반드시 실기기에서 확인해야 합니다.**
  안전한 대안: `wake()` 안에서 `Tone.start()` 만 클릭 핸들러에 남기고,
  무거운 `boot()` 본문만 다음 프레임으로 미룹니다.
  ```
  function wake(){
    if(HAS_TONE) Tone.start();          // 제스처 안에서 즉시 (가벼움)
    else if(ctx && ctx.state==='suspended') ctx.resume();
    boot();                              // 무거운 쪽
  }
  ```
  → `Tone.start()` 를 먼저 부르면 `ctx` 가 없어도 되는지 `graph.js` 의 `boot()`
  선행 조건을 확인해야 합니다(현재 `boot()` 이 `ctx` 를 만듭니다). 소유 팀 판단 필요.
- **충돌 위험: 높음.** `start()`/`stop()` 은 시퀀서 담당의 핵심 함수입니다.
  **6-3(프리베이크)을 먼저 하면 boot 가 짧아져 이 변경의 필요성이 줄어듭니다.**
  둘 중 하나만 한다면 6-3 을 권합니다.

## 6-3. [P1] 프리베이크 — 유휴 시간에 미리 굽기

**파일 A:** `src/audio/graph.js` — `boot()` 안의 세 곳

1. 화이트 노이즈 (147~154행): `for(let i=0;i<len;i++) nd[i]=Math.random()*2-1;`
2. 핑크 노이즈 (165~182행): 7탭 IIR 루프
3. 임펄스 응답 (111~113행): `IR.room/plate/hall = makeIR(...)`

**바꿀 방식:** 굽는 부분을 `AudioContext` 와 분리해 `Float32Array` 로 먼저 만들고,
`boot()` 은 그 배열을 `AudioBuffer` 에 복사만 합니다.

```
/* graph.js 최상단 근처 — AudioContext 없이 계산되는 부분 */
let BAKED = null;                  // {white:Float32Array, pink:Float32Array, ir:{room,plate,hall}}
const BAKE_RATE = 48000;           // 실기 sampleRate 와 다르면 boot 에서 다시 굽는다

function bakeBuffers(rate){
  const len = rate*4;
  const white = new Float32Array(len);
  for(let i=0;i<len;i++) white[i]=Math.random()*2-1;
  const pink = new Float32Array(len);
  { let b0=0,b1=0,b2=0,b3=0,b4=0,b5=0,b6=0;
    for(let i=0;i<len;i++){ const w=Math.random()*2-1;
      b0=0.99886*b0+w*0.0555179; b1=0.99332*b1+w*0.0750759;
      b2=0.96900*b2+w*0.1538520; b3=0.86650*b3+w*0.3104856;
      b4=0.55000*b4+w*0.5329522; b5=-0.7616*b5-w*0.0168980;
      pink[i]=(b0+b1+b2+b3+b4+b5+b6+w*0.5362)*0.11; b6=w*0.115926; } }
  return {rate, white, pink};
}
```

`boot()` 안에서는 이렇게 바뀝니다.

```
const use = (BAKED && BAKED.rate === ctx.sampleRate) ? BAKED : bakeBuffers(ctx.sampleRate);
const nb = ctx.createBuffer(1, use.white.length, ctx.sampleRate);
nb.getChannelData(0).set(use.white);          // 루프 → set() 한 번
const pb = ctx.createBuffer(1, use.pink.length, ctx.sampleRate);
pb.getChannelData(0).set(use.pink);
```

**파일 B:** `src/main.js` — `init()` 즉시실행 함수 **뒤**, 마지막 줄

```
/* 첫 화면이 뜬 뒤의 유휴 시간에 노이즈·IR 을 미리 굽는다.
   PLAY 첫 클릭의 boot() 가 133~293ms 메인 스레드를 잡는 원인이 이 굽기다
   (docs/ux/01-체감성능과대기심리.md). 사용자가 화면을 읽고 PLAY 를 찾는
   1~2초가 이 예산이다 — FCP(224ms) 와 domInteractive(283ms) 뒤이므로
   첫 로딩 시간에는 영향이 없다. */
(function prebake(){
  const run = () => { try{ BAKED = bakeBuffers(BAKE_RATE); }catch(e){} };
  if('requestIdleCallback' in window) requestIdleCallback(run, {timeout:2000});
  else setTimeout(run, 300);
})();
```

- ⚠ `sampleRate` 가 48000 이 아닌 기기(44100 등)에서는 `BAKED` 를 못 쓰고
  `boot()` 이 다시 굽습니다. 그 경우 이득이 0 이 되지만 **손해도 없습니다**
  (유휴 시간에만 굽고 버림). 실측 환경은 48000 이었습니다.
- `makeIR` 도 같은 방식으로 뺄 수 있으나 `ctx` 를 쓰는지 확인이 필요합니다
  (`makeIR` 은 `src/core/util.js` 에 있을 것으로 보이며 미확인 — 소유 팀 확인 요청).
- **충돌 위험: 중.** `boot()` 의 노이즈 블록만 만지므로 국소적입니다.
  `main.js` 는 30줄짜리라 충돌 가능성이 낮습니다.

# 부록 B. 측정 방법 (재현용)

- `boot()` 시간: `window.boot` 을 감싸 `performance.now()` 차이를 잼.
  `graph.js` 는 클래식 스크립트라 `function boot(){}` 이 `window.boot` 이 되고,
  `wake()` 안의 `boot()` 호출이 전역 객체를 거치므로 래퍼가 걸립니다.
- 오디오 시작 시각: `rawContext.currentTime` 과 `Tone.Transport.seconds` 를
  **1 ms `setInterval`** 로 샘플링해, 트랜스포트가 돌기 시작한 오디오 시계 시각을
  역산했습니다(`ctx시각 − Transport.seconds`).
  ⚠ `requestAnimationFrame` 폴링은 headless 에서 스로틀링되어(한 프레임이 779 ms 로
  측정된 사례 있음) **쓰지 않았습니다.**
- AnalyserNode 로 마스터를 탭해 파형 온셋을 잡으려 했으나, Tone.js 14 는
  `standardized-audio-context` 를 쓰므로 노드가 전역 `AudioNode` 의 인스턴스가
  아니고 `Tone.connect` 도 재할당되지 않아(측정 확인) **탭에 실패했습니다.**
  또 `AudioParam.prototype` · `AudioBufferSourceNode.prototype` 전역 후킹은
  페이지를 재로딩시켰습니다. 그래서 오디오 온셋은 **오디오 시계 역산 + 코드 상수**
  로 구했고, 본문에 「유도」 로 표시했습니다.
- 캐시 없는 로드: CDP `Network.clearBrowserCache` + `Network.setCacheDisabled`.
  Slow 4G: `Network.emulateNetworkConditions` (RTT 150 ms, 1.6 Mbps, 750 kbps up).
- 첫 방문 상태: `localStorage.clear()` 후 재로드.
