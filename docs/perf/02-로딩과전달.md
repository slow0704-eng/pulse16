## 1. 측정 방법과 조건

| 항목 | 내용 |
|---|---|
| 도구 | Playwright MCP (Chromium) + `curl` |
| 대상 | 배포본 GitHub Pages (로컬 서버 아님) |
| 위치 | 한국, 유선. TTFB 3–15 ms — **CDN 엣지가 매우 가까움** |
| 기기 | 데스크톱. 실측 CPU 수치는 **중급 모바일보다 3–5배 빠릅니다** |
| 바이트 | `curl -H "Accept-Encoding: gzip"` 의 `size_download` + 브라우저 `encodedBodySize`, **두 방법이 일치** |
| 회선 흉내 | **미측정.** 이 MCP 에는 CDP 스로틀링이 없어 `browser_evaluate` 로 회선을 조절할 수 없습니다. 회선별 수치는 전부 실측 바이트에서 **계산한 〈추정〉** 입니다 |

### 측정 중 만난 두 가지 함정 (기록용)

- **브라우저 공유.** 같은 Playwright 인스턴스를 다른 팀도 쓰고 있어 탭이 측정 중에
  가로채졌습니다. 그래서 모든 측정에 `location.pathname` 을 같이 찍어 어느 페이지를
  잰 것인지 확인했고, 확인 안 된 회차는 버렸습니다.
- **자동 부팅 오염.** 앞 회차에서 Play 를 누르면 `localStorage`(`pulse16.mk16.v1`, 4000자)
  가 남아 다음 로드가 «이미 booted» 상태로 시작합니다. 매 회차 `booted === false` 를
  확인하고서 측정했습니다.

### 2.2 압축은 실제로 걸립니다 — 확인했음

- GitHub Pages: `Content-Encoding: gzip`, `Vary: Accept-Encoding` ✔
- cdnjs: `Content-Encoding: br` (brotli) ✔ · `max-age=30672000, immutable`
- 전체 JS·CSS 압축률 **0.237** (871 KB → 206 KB), 브라우저 `encodedBodySize` 로 재확인
- 압축 안 되는 파일은 `_raw.js` **하나** (280 B → 270 B). 너무 작아서 무의미

### 2.3 프로토콜 — 42개 요청은 줄 서지 않습니다

`nextHopProtocol` 실측: **h2 26개 · h3 2개**. GitHub Pages 는 HTTP/2 입니다.
39개 JS 는 **한 연결에서 멀티플렉싱**되므로 HTTP/1.1 시절의
«6개씩 7번 왕복» 직렬화는 **일어나지 않습니다.**

- 46개 병렬 재수신: **239.6 ms**
- 같은 것을 1개씩 직렬로: 요청당 **22.6 ms** → 46개면 **634 ms** 〈추정〉

**이것이 번들링의 기대효과를 크게 깎습니다.** 요청 수 자체는 이미 싼 편입니다.
남는 비용은 파일당 헤더와, RTT 가 큰 회선에서의 혼잡 제어입니다.

### 2.4 진짜 직렬 구간 — 워터폴에서 줄 서는 곳

멀티플렉싱 덕에 «많은 파일» 은 문제가 아니고, **의존 사슬**이 문제입니다.

```
① HTML  ─(3 RTT 핸드셰이크 + 전송)─┐
②                                  ├─ styles/*.css  ─┐
③                                  ├─ src/*.js × 39  ├─→ 파서 차단 → 페인트
④                                  ├─ Tone.js (cdnjs = 새 오리진, +3 RTT)
⑤                                  └─ fonts.googleapis (새 오리진, +3 RTT)
⑥                                          └─ woff2 ×5 (fonts.gstatic, 또 새 오리진 +3 RTT)
```

- **④⑤⑥ 이 최악의 사슬입니다.** 폰트는 `HTML → CSS → woff2` 3단이고 매 단계가
  새 오리진이라, 느린 회선에서 최대 **9 RTT 깊이**입니다 〈추정〉.
  Slow 3G(RTT 2 s) 면 그것만 18초입니다.
- **③ 이 페인트를 막습니다.** `<script>` 가 `</body>` 앞에 있어도 **파서 차단**이라,
  브라우저는 39개 JS 를 다 내려받고 **실행까지** 마쳐야 글자를 그립니다.
  실측에서 FCP 와 DCL 이 ±100 ms 안에 붙어 나오는 이유입니다.
- 진입점이 `/pulse16/` 면 `index.html` 의 `meta refresh` + `location.replace` 로
  **문서 왕복이 한 번 더** 붙습니다(601 B 이지만 Slow 3G 면 2초).

## 5. 실측 A/B — `defer` 한 단어

가장 중요한 발견이라 **실제로 재봤습니다.** 배포본 HTML 을 스크래치패드로 받아
(프로젝트 파일은 건드리지 않음) `src`/`href` 를 배포 오리진 절대 URL 로 바꾼 뒤,
`<script>` 40개 전부에 `defer` 만 추가한 사본과 원본을 같은 조건에서 비교했습니다.

| | FCP | 조작 가능(DCL) | load |
|---|---:|---:|---:|
| 원본 (파서 차단) | 528 / 548 | 664 / 624 | 685 / 698 |
| **`defer`** | 372 / 244 | 521 / 260 | 620 / 343 |
| **차이(평균)** | **−230 ms (−43 %)** | **−253 ms (−39 %)** | −210 ms |

**기능 동일성도 확인했습니다** (`defer` 사본에서):

- `window.Tone` 존재 ✔ · `HAS_TONE === true` ✔ → **로드 순서가 보존됩니다**
- 칩 **357개** (원본과 동일) · Kit 옵션 12 · 뱅크 슬롯 4 · 드럼 행 7 · 베이스 패드 8
- `#stat` = `"Tone.js 준비됨"` → `src/main.js` 정상 실행 ✔
- `booted === false` → 제스처 전에 오디오를 깨우지 않음 ✔
- 콘솔 에러 0

**왜 안전한가:** HTML 명세상 `defer` 클래식 스크립트는 **문서 순서대로** 실행됩니다.
«로드 순서가 곧 의존 순서» 라는 이 프로젝트의 규칙이 그대로 유지됩니다.
바뀌는 것은 실행 *시점*(파싱 완료 후, DCL 직전)뿐이고, `main.js` 는 지금도
DOM 이 다 파싱된 뒤에 도는 마지막 스크립트라 차이가 없습니다.
HTML 에 인라인 `<script>` 가 없고 `document.write` 도 없어 걸릴 것이 없습니다.

## 6. 트레이드오프 — 어느 쪽을 권하는지

### 6.1 번들링·미니파이 vs 「빌드 없이 열면 돈다」

**먼저 오해를 풀어야 합니다.** `ARCHITECTURE.md` 10행이 클래식 스크립트를 고른
이유는 «**ES 모듈은 CORS 로 막혀 `file://` 로 안 열린다**» 입니다.
그런데 **클래식 스크립트 39개를 순서대로 이어 붙인 결과물도 클래식 스크립트**입니다.
전역 렉시컬 스코프를 공유하는 성질도, 실행 순서도 동일합니다.
**즉 concat 은 `file://` 더블클릭 가치를 하나도 깨지 않습니다.** 깨는 것은 모듈화입니다.

그러면 남는 진짜 손실은 «저장소를 클론해서 `pulse16-mk16.html` 을 더블클릭하면
편집한 것이 바로 보인다» 는 **저작(authoring) 경험**뿐입니다.
이건 **원본을 그대로 두고 배포본만 합치면** 지킬 수 있습니다.

또 실측이 기대를 깎는다는 점도 정직하게 말해야 합니다: HTTP/2 멀티플렉싱이라
39 → 1 요청의 이득은 좋은 회선에서 **작습니다**(§2.3). 큰 이득은 RTT 가 큰 회선과
미니파이의 바이트(131.6 KB → **약 60 KB** gzip 〈추정〉)에서 나옵니다.

> **권고: 한다. 단 GitHub Actions 로 «배포본만» 합친다. 그리고 우선순위는 4순위 이하다.**
>
> - `src/` 원본과 42개 `<script>` 태그를 **그대로 둡니다** → 더블클릭 흐름 유지
> - Actions 가 HTML 의 `<script src>` 목록을 **읽어서** 그 순서대로 concat →
>   `dist/app.js` 1개 + `<script defer src="app.js">` 하나로 바꾼 HTML 을 배포
> - 순서를 손으로 관리하지 않는 것이 핵심입니다. HTML 이 유일한 진실이 됩니다
> - 1단계는 **concat 만**(무손실·디버깅 쉬움), 2단계에서 미니파이

### 6.2 Service Worker vs 캐시 무효화 혼란

**측정된 사실이 결론을 정합니다: GitHub Pages 의 `Cache-Control` 은 `max-age=600` 입니다.**
자체 자원 45개 전부 10분입니다. 그리고 **Pages 에서는 이 값을 바꿀 수 없습니다.**

즉 10분 지나 다시 온 사람은 아무것도 안 바뀌었어도 **45개 조건부 요청**(`If-None-Match`
→ 304)을 보냅니다. h2 라 바이트는 싸지만 왕복은 실재합니다 —
Slow 3G(RTT 2 s) 면 «아무것도 안 바뀐 재방문» 에도 수 초가 듭니다.
`max-age` 를 못 만지는 이 제약이 **바로 SW 를 써야 하는 이유**입니다.
`<meta http-equiv>` 로는 안 됩니다(브라우저가 무시합니다).

혼란은 **해결 가능한 설계 문제**입니다.

> **권고: 한다. 단 «조용한 자동 갱신» 을 절대 하지 않는다.**
>
> - 프리캐시 이름에 **빌드 스탬프**를 박습니다: `pulse16-<git sha>`
> - **`skipWaiting()` 을 쓰지 않습니다.** 새 SW 는 `waiting` 에 둡니다
> - 새 버전이 대기 중이면 화면에 한 줄 띄웁니다:
>   «새 버전이 있습니다 — 새로고침» + 버튼. 사용자가 누를 때만 교체합니다
>   → «갱신이 안 보이는» 혼란이 «갱신을 사용자가 확정하는» 흐름으로 바뀝니다
> - **연주 중에 절대 교체하지 않습니다.** 오디오 그래프가 살아 있는 동안의 리로드는
>   소리를 끊습니다. `playing === true` 면 안내만 하고 대기시킵니다
> - 샘플(`tonejs.github.io`)은 프리캐시가 아니라 **stale-while-revalidate** 런타임 캐시
> - 얻는 것: 재방문 **45요청 → 0**, 그리고 **오프라인 동작**.
>   빌드 도구 없는 단일 파일 악기에 오프라인은 성격상 잘 맞는 기능입니다

### 6.3 폰트 자체 호스팅 vs 저장소 크기

측정: **woff2 5개 = 104,196 B**, CSS 1개 10,193 B, **오리진 2개**(`fonts.googleapis.com`,
`fonts.gstatic.com`), 그리고 `HTML → CSS → woff2` **3단 직렬 사슬**(§2.4).
`preconnect` 가 걸려 있어 완화는 되지만 사슬 자체는 남습니다.

저장소 비용 104 KB 는 — 이 앱이 이미 피아노 샘플 **1.26 MB** 를 외부에서 끌어오고
JS 원본이 491 KB 인 것에 비하면 **사실상 공짜**입니다.

> **권고: 한다. 강하게. 3순위급.**
>
> - woff2 5개를 `fonts/` 에 넣고 `styles/tokens.css` 에 `@font-face` 를 직접 씁니다
> - `font-display: swap` **유지** (CLS 0 을 측정했으므로 회귀 감시 지표가 있습니다)
> - 라틴 서브셋만 남기면 104 KB → **약 40 KB** 〈추정〉. 한글은 이 폰트들에 없고
>   UI 한국어는 시스템 폰트로 떨어지므로 손실이 없습니다
> - `preconnect` 2줄은 **삭제**합니다 (자체 호스팅 후엔 낭비)
> - 부수 효과: 오리진 2개와 3단 사슬이 사라져 Fast 3G 에서 **−0.8 ~ −1.1 s** 〈추정〉
> - 부수 효과 2: `file://` 로 열 때도 폰트가 나옵니다 (지금은 오프라인이면 시스템 폰트)

**Tone.js 도 같은 논리로 자체 호스팅을 권합니다.** cdnjs 는 brotli(66.7 KB)와
`immutable` 1년 캐시라 그 자체로는 훌륭하지만, **새 오리진 핸드셰이크 3 RTT** 가
붙습니다. 자체 호스팅하면 gzip 이라 바이트는 조금 늘지만(추정 +15 KB) 오리진이
하나로 줄고, `file://` 오프라인에서도 Tone 이 살아납니다.

### 6.4 샘플을 외부 CDN 에서 받는 것 vs 자체 호스팅

측정한 사실:

| 대상 | 요청 | 크기 | 비고 |
|---|---:|---:|---|
| 드럼킷 11종 × 6파일 | 66 | ~190 KB 〈추정, CR78 실측 17,265 B × 11〉 | **기본 경로** |
| 피아노(salamander) 13음 | 13 | **1,289,227 B (1.26 MB)** | 필요할 때만 |
| 배경 루프 6개 | 6 | **327,198 B (319 KB)** | 필요할 때만 |
| Casio 13음 | 13 | (미측정) | 필요할 때만 |

`tonejs.github.io` 는 `Access-Control-Allow-Origin: *` 이고 `max-age=600` 입니다 —
**그 자체가 제3자의 GitHub Pages 사이트이고 SLA 가 없습니다.**
죽으면: `src/audio/sampler.js:18` 의 `showWarn` 과 합성 폴백이 있어 **소프트 페일**
하지만, 「전체 받기」와 피아노 베이스 엔진은 **그냥 고장납니다.**

> **권고: 쪼갠다. 애매하게 두지 않는다.**
>
> - **드럼킷 11종(~190 KB)은 자체 호스팅한다 — 한다.**
>   「Kit 일괄 적용」·「전체 받기」는 사용자가 **가장 먼저 누르는 기본 경로**입니다.
>   핵심 경험의 단일 실패점을 190 KB 로 없앨 수 있으면 사는 게 맞습니다.
>   JS 원본 491 KB 를 이미 저장소에 두고 있으니 일관성도 있습니다
> - **피아노 1.26 MB · 루프 319 KB 는 외부에 둔다 — 하지 않는다.**
>   저장소를 8배로 불리는데 쓰는 사람이 적고, 합성 폴백이 실제로 동작합니다
> - 대신 **실패를 정직하게 보여줍니다.** 지금 `blocked()` / `showWarn` 이 있으니,
>   문구에 «외부 샘플 서버가 응답하지 않습니다 — 합성 엔진으로 계속합니다» 처럼
>   *복구되었다* 는 사실까지 담습니다
> - `AUDIO_BASE` 를 상수 하나로 두는 현재 구조(`src/core/config.js:9`)가 좋습니다.
>   자체 호스팅분과 외부분이 갈리면 상수 **두 개**로 나누세요

## 10. 회선별 «3초 안에 소리» — 계산값 〈전부 추정〉

   그리고 Actions 안에서만 존재해야 합니다. 로컬에 `npm install` 을 요구하는 순간
   지키려던 것이 사라집니다.

3. **42개 스크립트에 `<link rel="preload">` 를 걸지 마세요.**
   실측: 첫 JS 요청이 **56 ms** 에 시작하고 마지막이 **58 ms** 에 끝납니다 —
   파서가 이미 전부 즉시 발견해 h2 로 한 번에 받습니다.
   preload 42줄은 HTML 만 키우고 이득이 0 이며, 잘못 쓰면 이중 요청이 됩니다.
   **`defer` 가 정답이고 preload 는 아닙니다.**

4. **CSS 를 HTML 에 인라인하지 마세요.**
   전체 CSS 가 gzip **7,434 B** 이고 LCP 216 ms · CLS 0 입니다. 병목이 아닙니다.
   인라인하면 CSS 캐시가 사라지고 HTML 이 매번 커집니다.

5. **«워밍업» 이라며 로드 시점에 `boot()` 을 부르지 마세요.**
   ① 크롬 자동재생 정책상 제스처가 없으면 컨텍스트가 `suspended` 라
   결국 `resume` 지연을 또 냅니다 ② 234 ms 를 **로드 경로로 옮기는 것**이라
   TTI 가 그만큼 나빠집니다 ③ Play 를 안 누를 방문자에게도 노드 수백 개와
   **1.46 MB 버퍼**와 상시 구동 오실레이터 6개를 물립니다.
   올바른 방향은 §8.2 처럼 **boot 자체를 가볍게** 만드는 것입니다.

6. **노이즈 버퍼를 «최적화» 하지 마세요.**
   합쳐 **11.9 ms** 입니다(실측). 4초 길이나 샘플레이트를 건드리면
   음색이 바뀔 위험만 있고 얻을 시간이 없습니다. 범인은 §4.1 의 기타 이펙트입니다.

7. **Tone.js 를 걷어내지 마세요.**
   brotli **66.7 KB** 로 Transport 스케줄링·`Sampler`·`Player`·기타 3이펙트를 삽니다.
   `HAS_TONE === false` 폴백은 존재하고 꽤 완성돼 있지만(네이티브 컴프레서·
   `AnalyserNode` 미터·`nativeWidener()`·`setInterval(fbLoop,25)` 대체 클럭),
   **샘플 기능 전체가 비활성**(`UI.kit`·`preload`·`cload` 가 `disabled`)이고
   기타 페이저·와·코러스도 사라집니다. 대체가 아니라 **비상용**입니다.

8. **`<meta http-equiv="Cache-Control">` 로 캐시를 늘리려 하지 마세요.**
   브라우저가 무시합니다. GitHub Pages 의 `max-age=600` 은 바꿀 수 없고,
   그래서 답이 Service Worker 입니다(§6.2).

9. **SW 에서 `skipWaiting()` + 자동 리로드를 쓰지 마세요.**
   연주 중에 페이지가 갈리면 소리가 끊깁니다. 사용자가 갱신을 **확정**하게 하세요.

10. **`src/` 파일 순서를 바꾸거나 `id` 와 같은 이름의 최상위 함수를 만들지 마세요.**
    성능 작업 중에도 유효한 제약입니다 (`ARCHITECTURE.md` 18·25행).

## 부록 — 재현 방법

`boot()` 세부와 제스처→소리를 다시 재려면 (배포본에서):

1. 새 탭으로 배포본을 엽니다. **`booted === false` 를 먼저 확인** — 아니면
   `localStorage.clear()` 후 새로고침 (§1 의 오염 함정)
2. `window.boot` 를 감싸 실행시간을 재고, 그 안에서 `tpClip` 에 `AnalyserNode` 를 달아
   `getFloatTimeDomainData` 피크가 0.005 를 넘는 순간을 `requestAnimationFrame` 으로 잡습니다
   (최상위 `function` 선언은 전역 프로퍼티라 `window.boot` 로 교체됩니다.
   `ctx`·`tpClip` 은 `let` 이라 `window` 에 없지만 맨 식별자로는 참조됩니다)
3. `keydown` 을 캡처 단계에서 찍어 제스처 시각을 잡고, **Space** 를 실제로 누릅니다
   (합성 클릭이 아니라 진짜 제스처여야 오디오가 깨어납니다)
4. 브라우저를 다른 세션과 공유한다면 **매 측정에 `location.pathname` 을 같이 찍어**
   어느 페이지를 잰 것인지 확인하세요
