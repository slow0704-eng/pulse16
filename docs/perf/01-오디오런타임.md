# PULSE·16 오디오 런타임 성능 — 실측 보고서

작성: 2026-08-08 · 담당: 실시간 오디오 런타임
대상: `src/audio/*` · `src/core/util.js` · `src/core/state.js` · `src/seq/sequencer.js` · `src/ui/meters.js`
**이 문서는 읽기·측정만 한 결과입니다. `src/` 는 한 글자도 고치지 않았습니다.**

---

## 0. 한 문단 요약

> 이 앱의 끊김은 **보이스가 무거워서가 아닙니다.** Tone.js 14.7.77 이 `rawContext` 로
> 내주는 컨텍스트가 네이티브 `AudioContext` 가 아니라 **standardized-audio-context(SAC) 래퍼**이고,
> 앱의 모든 `ctx.createX()` · `param.setValueAtTime()` · `node.connect()` 가 그 래퍼를 통과합니다.
> 같은 앱 코드로 A/B 한 실측에서 그래프 조작 단가가 **12배~870배** 차이났습니다.
> 기타 한 음을 앰프 체인에 잇는 `connect()` 한 줄이 **12 ms**(네이티브 0.0095 ms)입니다.
> 가장 무거운 조건의 `onTick` 중앙값이 **275 ms**(스텝 간격 75 ms)에서
> 네이티브 컨텍스트로 갈아끼우면 **6.5 ms** 로 떨어집니다 — 앱 코드는 그대로 두고 `boot()` 앞 3줄만 바꿔서.
>
> 두 번째 원인은 `bakeStruck()` 입니다. 피아노 한 음을 굽는 데 **222~323 ms** 동안 메인 스레드가 멈춥니다.
> 180초 실사용 재생에서 굽기로만 **4.74초** 가 통째로 정지했고, 최악의 한 스텝은 **1.30초** 멈췄습니다.
>
> rAF 미터 루프와 DOM 갱신은 **문제 없음**입니다(각각 0.06 ms/프레임, 0.11 ms/루프).
> 오히려 과부하 때 미터가 오디오에 굶어 죽습니다(rAF 간격 최대 4.9초).

> 되돌아가 버려서 측정이 계속 오염됐습니다. 그래서 저장소에 이미 들어 있는

### 1-2. 계측 방식 — 앱 코드를 고치지 않는 심(shim)

앱의 최상위 `function` 선언은 전역 객체 프로퍼티라 **런타임에 감쌀 수 있습니다.**
호출부가 자유 식별자로 참조하므로 래퍼가 실제로 걸립니다. 페이지 로드 직후·`boot()` 전에 이렇게 걸었습니다.

* `onTick` / `fbLoop` — 처리시간, 그 안에서 만들어진 노드 수, **예약 여유** `lead = (t − ctx.currentTime)×1000`
* `acqGain` / `acqBQ` — 풀 적중·실패
* `ksRender` / `bakeStruck` — 굽기 1회 비용(= 캐시 미스 1회)
* `sweep` — 1회 비용, 큐 길이, `liveNodes`, 풀 잔량
* `meterLoop` / `drawStep` — rAF 간격, 프레임당 비용
* `boot` — 반환 직후 `ctx.createX()` 를 인스턴스에 덮어써서 종류별 생성 수를 셈

`liveNodes` 는 앱 자신의 카운터인데 **버그가 있어 신뢰할 수 없습니다**(§3-6). 대신 `retireQ.length` 를
«지금 살아 있는 일회용 노드» 의 대리 지표로 봤습니다.

### 1-3. 시나리오 (전부 BPM 200 = 16분음표 스텝 **75.0 ms**, 초당 13.33 스텝, `chance` 노브 0 → 확률 스킵 없음)

| 이름 | 내용 |
|---|---|
| **LIGHT** | 전형적 패턴. 킥 2·스네어 2·클로즈햇 8·베이스 2음·건반 화음 1회·기타 1음 / 마디. `kick deep, snare crack, chat noise, bass sub, keys pad, gtr clean` |
| **REAL** | 과제가 지정한 «가장 무거운 조건». 드럼 7트랙 + 베이스 + 건반 4음 화음 + keys2 + 기타 2트랙 + **선율·리프·베이스라인 + 필인 + 화성 진행 + 그루브 + 옥타브 겹침**. 엔진은 무거운 쪽으로: `clap hall · tom timbale · perc guiro · bass moog · keys supersaw · keys2 strings · gtr hi · gtr2 clean` |
| **MAX** | 위와 같은 엔진에 **16스텝 전부를 강제로 채운** 있을 수 없는 최악. 실제 프리셋에는 이런 패턴이 없습니다 — 상한을 보려고 넣었습니다 |
| **LONG** | 180초. 굽는 엔진만 골라서 `keys piano · keys2 vibes · gtr sitar · gtr2 steel · bass upright`, 선율·필인·화성·그루브 켜고 **패턴 셔플 4루프마다**(= 틀어놓고 듣는 실제 용법) |

각 시나리오를 **① Tone 기본(SAC)**, **② `Tone.setContext(new Tone.Context(네이티브 AudioContext))`**,
**③ Tone CDN 차단(= `HAS_TONE=false` 폴백 경로, 순수 네이티브)** 세 모드로 돌려 A/B 했습니다.

### 1-5. 못 잰 것 — 정직 원칙

| 항목 | 상태 | 이유 |
|---|---|---|
| **AudioContext 언더런 횟수 / 오디오 스레드 부하율** | **미측정** | `AudioContext.renderCapacity`(Chrome 112+) 가 이 브라우저에서 **SAC 컨텍스트에도, 네이티브 컨텍스트에도 노출되지 않았습니다.** 헤드리스에는 실제 출력 장치도 없습니다. 그래서 «오디오 스레드가 몇 번 굶었는가»는 잴 방법이 없었습니다. |
| **실제 청감(끊김 소리)** | **미측정** | 헤드리스에 사운드 카드가 없습니다. |
| `ctx.outputLatency` (Tone 경로) | **측정 불가** | SAC 가 구현하지 않아 `undefined`. 네이티브 컨텍스트에서는 0.024~0.040 s 로 나옵니다. |
| 실기(사운드 카드 있는 데스크톱/모바일)의 절대 수치 | **미측정** | 아래 표의 ms 는 이 환경의 실측입니다. 기계가 바뀌면 절대값은 변하지만 **A/B 배율은 남습니다.** |

**헤드리스의 큰 왜곡 하나를 꼭 알아 두십시오.** 출력 장치가 없어서 `ctx.currentTime` 이 벽시계보다
느리게 흐릅니다(실측: LIGHT 에서 15 % 지연, MAX 에서 45 % 지연). 그래서
**«지각한 스텝 수»는 절대값으로 믿지 마십시오.**
1차 지표는 시계와 무관한 **`performance.now()` 기반 `onTick` 처리시간 대 스텝 간격(75 ms)** 입니다.
이 지표는 «음악 1초를 만드는 데 메인 스레드가 몇 초를 쓰는가» 로 환산할 수 있고, 그 값이 1을 넘으면
어떤 기계에서도 반드시 끊깁니다.

## 2. 컨텍스트·지연 실측

| 항목 | Tone 기본(SAC) | 네이티브 컨텍스트 |
|---|---|---|
| `ctx.sampleRate` | 48 000 | 48 000 |
| `ctx.baseLatency` | **0.010 s** | **0.010 s** |
| `ctx.outputLatency` | **undefined** (SAC 미구현) | **0.024 ~ 0.040 s** |
| `Tone.getContext().lookAhead` | **0.08 s** (graph.js:22 에서 설정) | 0.08 s |
| 총 예약 지연(합) | ≈ 0.09 s + α | **0.114 ~ 0.130 s** |
| `renderCapacity` | 없음 | 없음 |

`lookAhead 0.08` 은 «최대 80 ms 안에 onTick 이 끝나야 한다»는 뜻이 아니라
«오디오 시각보다 80 ms 앞서 예약한다»는 뜻입니다. 스텝 하나를 만드는 데 75 ms 를 넘게 쓰면
lookAhead 여유가 스텝마다 깎여 나가고, 여유가 0 이 되는 순간부터 **이미 지나간 시각에 예약**하게 됩니다
(웹오디오는 과거 시각 예약을 «지금 즉시»로 처리 → 어택이 뭉치고 리듬이 흐트러집니다).
아래 표의 `lead ≤ 0` 이 그 순간입니다.

> 표기 규칙 — **[실측]** 은 이 환경에서 직접 잰 값, **[역산]** 은 실측값끼리 나눠 얻은 값,

### 3-1. `onTick` 처리시간 분포 (핵심 표) **[실측]**

BPM 200 → 스텝 간격 **75.0 ms**, 초당 13.33 스텝. 40초 재생(LONG 만 180초).

| 시나리오 / 모드 | p50 | p90 | p99 | max | >75 ms | `lead≤0` | **음악 1초당 메인스레드 CPU**(p50 기준) [역산] |
|---|---:|---:|---:|---:|---:|---:|---:|
| LIGHT / Tone(SAC) | **0.7** | 7.6 | 70.6 | 92.0 | 4 / 451 | 5 (1.1 %) | 0.009 s (0.9 %) |
| REAL / Tone(SAC) | **29.5** | 79.6 | 209.9 | 252.0 | 34 / 277 | 24 (8.7 %) | **0.39 s (39 %)** |
| MAX / Tone(SAC) | **275.1** | 438.4 | 613.9 | 613.9 | 96 / 96 | 67 (70 %) | **3.67 s (367 %)** ← 물리적으로 불가능 |
| REAL / **네이티브 컨텍스트** | **1.9** | 4.6 | 19.4 | 46.3 | 0 / 533 | 0 | 0.025 s (2.5 %) |
| MAX / **네이티브 컨텍스트** | **6.5** | 9.6 | 16.3 | 46.2 | 0 / 533 | 0 | 0.087 s (8.7 %) |
| MAX / **HAS_TONE=false 폴백**(`fbLoop`) | 0.0 | 4.8 | 7.9 | 64.2 | 0 / 1594 | 0 | — (호출당 여러 스텝을 묶어 예약해 직접 비교 불가) |

읽는 법:

* **REAL(과제가 지정한 무거운 조건) 에서 이미 p90 이 스텝 간격을 넘습니다.** 열 스텝에 한 번씩 밀립니다.
* MAX 에서는 40초 동안 스텝이 **96개** 밖에 안 나갔습니다(정상이라면 533개). 트랜스포트 자체가 굶었습니다.
* 네이티브 컨텍스트로 바꾸면 **같은 MAX 시나리오에서 스텝이 533개 전부 나가고**(5.5배 많은 일)
  그러면서 스텝당 비용이 275 → 6.5 ms 로 떨어집니다. 총 처리량 기준 **약 230배**입니다.
* LONG 의 max 1299.6 ms 는 굽기(§3-5)가 한 스텝에 몰린 것입니다.

### 3-2. 그래프 조작 단가 A/B — **이 보고서의 핵심** **[실측]**

같은 페이지 안에서, 같은 코드가 부르는 같은 API 를 두 컨텍스트로 재봤습니다.

| 연산 | Tone `rawContext` (SAC) | 네이티브 `AudioContext` | 배율 |
|---|---:|---:|---:|
| `createGain()` | 14.9 ~ 37.0 µs | 7.3 µs | 2 ~ 5× |
| `createBiquadFilter()` | 30.7 ~ 78.7 µs | 19.9 µs | 1.5 ~ 4× |
| `createOscillator()` | 30.5 ~ 42.8 µs | 8.1 µs | 4 ~ 5× |
| `createBufferSource()` | 50.1 µs | 7.2 µs | 7× |
| `param.setValueAtTime()` | 15.7 ~ 23.8 µs | **0.55 ~ 0.8 µs** | **20 ~ 43×** |
| `param.linearRampToValueAtTime()` | 15.5 µs | 0.6 µs | **26×** |
| `param.value = x` | 29.5 µs | 2.4 µs | 12× |
| `param.cancelAndHoldAtTime()` (= `hold()`) | **107 ~ 111 µs** | **2.2 ~ 2.9 µs** | **38 ~ 43×** |
| `connect()` → 빈 게인 | 22 µs | 10 µs | 2× |
| `connect()` → `chan.keys` (마스터 체인에 연결됨) | **318 ~ 384 µs** | **9.9 ~ 11.4 µs** | **32 ~ 39×** |
| `connect()` → `ampIn.amp_hi` (앰프 25단 체인) | **8 157 ~ 12 082 µs** | **9.3 ~ 9.5 µs** | **870 ~ 1 270×** |

**SAC 의 `connect`/`disconnect` 비용은 «연결된 하류 그래프의 크기» 에 비례합니다.**

**기타 한 음을 앰프에 잇는 `connect()` 한 줄이 12 ms** 가 됩니다.

**수명** — `G()`/`BQ()` 는 `retire(node, kind, end+0.05)` 로 걷습니다(`util.js:181-182`).

따라서 노드 수명 = 음 길이 + 50 ms + 최대 120 ms 의 회수 지연.

### 3-7. `sweep()` 의 비용 — 알고리즘이 아니라 `disconnect` 단가 **[실측]**

처음엔 `retireQ.splice(i,1)` 이 O(n²) 인 줄 의심했습니다. **아닙니다.**
가짜 노드로 큐만 키워 재보니 20 000개 회수에 **3.5~4.0 ms** 였습니다(항목당 0.17 µs).

진짜 비용은 `node.disconnect()` 입니다 — 마스터에 붙어 있던 SAC 노드 하나를 떼는 데 **245~301 µs**
(네이티브 0.25~0.75 µs). MAX/SAC 에서 큐가 11 210개까지 밀렸을 때 `sweep()` 1회가 **4 908 ms** 걸린 것은
11 210 × ~0.25 ms ≈ 2.8 s 로 설명됩니다. 즉 **§3-2 와 같은 뿌리**입니다.

### 3-8. `liveNodes` 카운터는 틀렸습니다 **[실측]**

`liveNodes` 는 `acqGain()`/`acqBQ()` 에서만 `++` 되는데(`util.js:112,118`)
`sweep()` 은 **`retireQ` 의 모든 항목에서 `--`** 합니다(`util.js:129`).
그런데 `shaperNode()`·`tapNoise()`·`tapPink()`·`tapMetal()`·`keysVoice` 의 패너/보이스추적 정리·
`guitarVoice` 의 `gtrRef` 정리는 `retire(가짜객체,'x',t)` 로 걷습니다 — **`++` 없이 `--` 만 됩니다.**

최소 재현 **[실측]**: `acqGain()` 1 + `acqBQ()` 1 → `liveNodes = 2` (맞음) →
`retire(gain)`, `retire(bq)`, `retire({disconnect},'x')` 후 `sweep()` → **`liveNodes = −1`**.
킥 + supersaw + 기타 clean 한 세트에 `'x'` 종류 retire 가 **10개** 붙습니다.

실제로 40초 재생 후 `liveNodes = −6 450`, 180초 후 **`−10 318`** 이 나왔습니다.
`meters.js:94` 가 화면에 찍는 `nodes N` 은 그래서 **음수로 흐릅니다.**
성능 문제는 아니지만, **성능을 관측하는 눈이 고장 나 있다**는 뜻이라 먼저 고쳐야 합니다.

## 5. 항목별 처방

### ① Tone 을 네이티브 `AudioContext` 위에 올린다 — **최우선**

* **무엇을** — 앱의 모든 웹오디오 호출이 SAC 래퍼를 지나가는 것을 멈춘다.
* **어느 파일 어느 함수** — `src/audio/graph.js` `boot()` 20~26행.
* **구체적 명세** — 지금:

  ```js
  if(HAS_TONE){
    ctx = Tone.getContext().rawContext;        // ← 이게 SAC 래퍼다
    Tone.getContext().lookAhead = 0.08;
  }
  ```

  바꿀 것:

  ```js
  if(HAS_TONE){
    /* Tone 14 는 rawContext 로 standardized-audio-context 래퍼를 준다.
       그 래퍼를 통과하는 connect/param 예약이 네이티브보다 20~870배 비싸다
       (docs/perf/01-오디오런타임.md §3-2). Tone 을 우리가 만든 네이티브
       컨텍스트 위에 올려서, Tone 의 기능(Transport·Compressor·Meter·
       StereoWidener·Phaser·AutoWah·Chorus·Sampler·Player)은 그대로 쓰고
       노드 조작만 네이티브 속도로 되돌린다. */
    const nativeCtx = new (window.AudioContext||window.webkitAudioContext)(
                        {latencyHint:'interactive'});
    Tone.setContext(new Tone.Context(nativeCtx));
    ctx = Tone.getContext().rawContext;        // === nativeCtx (실측 확인)
    Tone.getContext().lookAhead = 0.08;
  }
  ```

  세 줄입니다. 나머지 코드는 한 글자도 안 바뀝니다.
* **기대 효과 [실측]** — REAL `onTick` p50 **29.5 → 1.9 ms**, p90 **79.6 → 4.6 ms**, 지각 스텝 24 → 0.
  MAX `onTick` p50 **275.1 → 6.5 ms** 이면서 처리한 스텝 수는 96 → 533 (5.5배).
  `gtr/hi` 보이스 **16.7 → 0.04 ms**. `ctx.outputLatency` 가 드디어 읽힙니다(0.024~0.040 s).
* **호환성 실측** — 네이티브 컨텍스트 위에서 다음이 **전부 정상 동작함을 확인했습니다**:
  `Tone.Compressor`(glue·lim) · `Tone.Meter`(−10.1 dB 정상 판독) · `Tone.StereoWidener` ·
  `Tone.Phaser`/`AutoWah`/`Chorus`(gtrFX 3종 생성 성공) · `Tone.Player`(16.00 s mp3 로드) ·
  `Tone.Sampler`(salamander 로드) · `ConvolverNode` 버퍼 · `Tone.Transport`(BPM 200 정확).
* **트레이드오프** — SAC 는 «브라우저 차이를 메우는 폴리필» 이기도 합니다. 벗으면 그 방패가 사라집니다.
  구체적으로 SAC 가 메워 주던 것과 **우리 코드의 현 상태**:

  | SAC 가 메우던 것 | 우리 코드 | 판단 |
  |---|---|---|
  | `cancelAndHoldAtTime`(사파리 미구현) | `util.js:147-150` `hold()` 가 없으면 `cancelScheduledValues` 로 폴백 **이미 있음** | 안전 |
  | `AudioBufferSourceNode.detune`(사파리 미구현) | `voice-gtr.js:80`, `struck.js:129` 가 `if(s.detune)` 분기 **이미 있음** | 안전 |
  | `createStereoPanner`(구형 미구현) | `graph.js:134`, `voice-keys.js:253` 가 분기 **이미 있음** | 안전 |
  | `AudioContext` 생성자 옵션 | 옵션 무시돼도 동작 | 안전 |
  | `AudioWorklet` 심 | 우리는 안 씀 | 무관 |

  **즉 이 프로젝트는 이미 «네이티브 편차» 를 스스로 방어하고 있습니다.** 과거 담당자들이 실측으로
  하나씩 잡아 둔 그 분기들이 그대로 보험입니다.
* **위험** — ① 사파리/구형 브라우저에서만 드러나는 회귀. 이 환경에서는 못 잽니다(**미측정**).

  ③ 되돌리기가 3줄이라 롤백 비용이 사실상 0 입니다.

     Blob 워커를 하나 띄운다. `ctx` 를 안 쓰는 순수 수학이라 그대로 옮겨집니다

  2. `struckBuf(name,midi,hz,S)` 가 캐시 미스일 때 **버퍼 대신 «준비 중» 을 돌려주고**
     워커에 요청한다. 도착하면 `ctx.createBuffer` + `copyToChannel` 로 캐시에 넣는다.
  3. 아직 안 구워진 음은 그 스텝만 **가장 가까운 이미 구워진 음정을 `playbackRate` 로 옮겨** 쓴다

* **file:// 에서 되는가 — [실측] 됩니다.** `new Worker(blob:)` 과 `new Worker(data:)` 둘 다
  `file://` 페이지에서 정상 동작했습니다(48 000 샘플 Float32Array 전송 왕복 성공).
  상대경로 워커(`new Worker('src/...')`)만 막힙니다. **빌드 도구 없이 가능합니다.**
* **기대 효과 [추정, 근거는 실측]** — LONG 180초 기준 메인스레드 정지 **4 353 ms → ≈0**.

* **트레이드오프** — 첫 음이 «정확한 그 음정»이 아니라 «옮겨 쓴 음정» 으로 한 번 울립니다.

* **위험** — 워커 왕복(≈수 ms) 동안 같은 키가 중복 요청될 수 있습니다 → «진행 중» 집합으로 막으십시오.

  → `bakeStruck` 본문을 함수 하나로 뽑아 `Function.prototype.toString()` 으로 워커에 넣으면 한 벌로 유지됩니다.
* **난이도** — **중간.** 비동기 경로가 하나 늘어납니다.
* **더 싼 임시방편** — 워커가 부담스러우면 **`struckVoice()` 를 부르기 전에 다음 마디에서 쓸 음정을
  `onLoopWrap()` 에서 미리 굽는 «선행 굽기»** 만 해도 절반은 잡힙니다. 어차피 `melNow`/`compNow` 가
  이미 다음 마디에 어떤 음이 나올지 알고 있습니다(`sequencer.js:502-519`). 다만 굽는 순간의
  정지는 그대로라, 루프 경계에 200 ms 짜리 구멍이 생깁니다 — **근본책이 아닙니다.**

### ④ 셔플이 만드는 캐시 재굽기를 줄인다

* **어느 파일** — `src/audio/string.js` `makeStringCache(limit)` 224~235행,
  `src/audio/voice-gtr.js:8` (24) · `src/audio/voice-bass.js:13` (20) · `src/audio/struck.js:93` (48).
* **구체적 명세** — ① 상한을 **엔진 수 × 도수** 기준으로 올린다(기타 24 → 64, 베이스 20 → 48).
  ② LRU 를 «삽입 순서» 가 아니라 **«최근 사용»** 으로 고친다 —
  지금 `m.get(key)` 로 적중해도 순서를 갱신하지 않아, 자주 쓰는 음이 먼저 밀려납니다:

  ```js
  let b=m.get(key);
  if(b){ m.delete(key); m.set(key,b); return b; }   // ← 이 두 줄이 빠져 있다
  ```
* **메모리 대가 [역산]** — 버퍼 하나 = 48 kHz × 평균 4.5 s × 4 byte ≈ **864 KB**.
  기타 64개면 **55 MB**. 지금(24개) 20 MB 에서 +35 MB.
  현재 힙이 REAL 에서 107 MB 이므로 무시할 크기가 아닙니다.
* **권장** — **상한을 «개수» 가 아니라 «총 바이트» 로 거십시오.** 예: 48 MB 를 넘으면 LRU 로 뺀다.
  버퍼 길이가 엔진마다 0.3 s ~ 9.0 s 로 30배 차이나는데 개수로 세는 것은 위험합니다
  (pedal steel 9 s × 24개 = 41 MB, mute 0.33 s × 24개 = 1.5 MB — 같은 «24개»입니다).
* **트레이드오프** — 메모리 ↔ 재굽기. `ksRender` 는 최악 12.5 ms 라 ①을 고친 뒤에는
  스텝 예산(75 ms) 안에 들어갑니다. **①·②를 먼저 하고 이건 나중에 재보고 결정하십시오.**
* **난이도** — 낮음. **위험** — 낮음(메모리만).

## 7. AudioWorklet 도입 여부 — **지금은 도입하지 않는다**

### 7-1. 제약 안에서의 실측

`file://` 로 앱을 직접 열었을 때(**앱은 `file://` 에서 정상 부팅합니다 — 실측 확인:
`appLoaded=true`, `HAS_TONE=true`, `ctx.state='running'`, 48 kHz**) 워클릿 모듈 적재 결과입니다.

| 방식 | http:// | **file://** |
|---|---|---|
| 네이티브 ctx + `addModule(blob:)` | **OK** | **실패** (`Unable to load a worklet's module`) |
| 네이티브 ctx + `addModule(data:text/javascript,...)` | **OK** | **OK** ✔ |
| 네이티브 ctx + `addModule('src/....js')` (상대경로) | OK | **실패** (`file://` fetch 차단) |
| **Tone(SAC) ctx** + `addModule(blob:)` | OK | **실패** |
| **Tone(SAC) ctx** + `addModule(data:)` | (미측정) | **실패** |

**결론: 워클릿은 `file://` 에서 «네이티브 컨텍스트 + `data:` URL» 조합으로만 됩니다.**
빌드 도구는 필요 없지만, **§5-① 을 먼저 해야 가능합니다**(SAC 컨텍스트로는 `file://` 에서 아예 안 됨).

참고로 **Web Worker 는 `file://` 에서 `blob:`·`data:` 둘 다 동작합니다**(실측).
즉 «메인 스레드에서 무거운 계산을 빼는» 목적이라면 워클릿이 아니라 워커가 정답입니다.

### 7-2. 왜 지금은 아닌가

1. **병목이 오디오 스레드가 아닙니다.** 실측된 병목은 전부 **메인 스레드의 그래프 조작 비용**입니다
   (§3-2). 워클릿은 그것을 **한 푼도** 줄이지 않습니다. 오히려 `AudioWorkletNode` 도 노드라
   생성·연결 비용을 똑같이 냅니다.
2. **대가가 지나칩니다.** 지금 구조는 「네이티브 노드 그래프 + 오프라인으로 구운 버퍼」입니다.
   워클릿으로 옮기려면 킥·스네어·햇·톰·퍼커션·베이스·건반·기타의 DSP 를 전부 다시 써야 합니다.
   그 과정에서 이 저장소에 축적된 실측 기반 튜닝(군지연 보정, 자와리, 픽업 콤, 트루피크 실링,
   퍼즈 3단 클리핑…)을 전부 다시 검증해야 합니다. **§5-① 은 3줄입니다.**
3. **`file://` 에서 소스가 문자열이 됩니다.** `data:` URL 이든 `Blob` 이든 워클릿 코드는 JS 문자열로
   인라인돼야 합니다. 이 프로젝트가 지키는 「빌드 도구 없이, 소스를 그대로 읽는다」 와
   정면으로 부딪히지는 않지만(빌드는 여전히 없음), **소스를 문자열 안에 넣는 순간
   `tools/_app-harness.js` 가 경고한 «복사본이 조용히 거짓말하는» 함정에 가까워집니다.**
4. **디버깅 난이도.** 워클릿 안에서는 브레이크포인트도 `console.log` 도 제한적이고,
   지금 저장소의 계측 문화(`tools/measure-*.html` 로 OfflineAudioContext 렌더 후 분석)를 그대로 못 씁니다.

### 7-3. 언제 재검토하는가 — 조건을 명시합니다

* **(A)** §5-① 과 ② 를 하고도 `onTick` p99 가 스텝 간격을 넘으면.
* **(B)** 오디오 스레드 부하를 실제로 잴 수 있게 됐을 때(실기 + `renderCapacity`), 그 부하가 70 % 를 넘으면.
  지금은 **미측정** 이라 판단할 근거가 없습니다.
* **(C)** 「구운 버퍼」를 버리고 **실시간 Karplus-Strong** 으로 가고 싶을 때.
  `string.js` 첫 주석이 적어 둔 «DelayNode 루프는 사이클당 128샘플 때문에 상한 SR/256 = 187.5 Hz,
  기타 G3(196 Hz)조차 못 낸다» 는 제약은 **워클릿만이 없앨 수 있습니다.**
  그때는 굽기·캐시·캐시미스가 통째로 사라지므로 §5-② 도 필요 없어집니다.
  그러나 그것은 성능 과제가 아니라 **음색 아키텍처 과제**입니다.

**요약: 워클릿은 «나중에, 음색 아키텍처를 바꿀 때» 의 카드입니다. 지금 끊김을 고치는 카드가 아닙니다.**

## 8. 부록 — 검증 과정에서 뒤집은 가설 (정직 기록)

성급하게 보고했다가 틀렸을 뻔한 것들입니다. 남겨 둡니다.

| 가설 | 결과 |
|---|---|
| 「기타는 음마다 다시 굽는다」 | **틀림.** 첫 계측 스크립트의 카운터 버그였습니다. 같은 (엔진\|음정)을 5번 불러 굽기는 1회. 16개 기타 엔진 계측에서 굽기도 정확히 16회. |
| 「`sweep()` 이 `splice` 때문에 O(n²)」 | **틀림.** 20 000개 회수에 3.5 ms(항목당 0.17 µs). 진짜 비용은 SAC `disconnect()` 245~301 µs. |
| 「rAF 미터가 오디오와 경쟁한다」 | **틀림, 반대.** 미터는 0.36 %. 과부하 때 오디오가 미터를 굶깁니다(rAF 간격 최대 4.9 s). |
| 「메모리가 샌다」 | **틀림.** 180초 진동, 단조 증가 없음. MAX 의 170 MB 는 회수 못 한 SAC 래퍼였습니다. |
| 「캐시 상한(48)이 재생 중에 터진다」 | **아직 아님.** 180초에 32개까지만 찼습니다. 다만 여유가 적고 LRU 갱신 누락이 있습니다(§5-④). |
| 「보이스당 노드가 너무 많다」 | **부분적으로만.** 41개(supersaw)는 많지만 네이티브에서 0.82 ms 입니다. 노드 수가 아니라 **노드 하나당 단가**가 문제였습니다. |

## 9. 권고 순서

1. **§5-③** `liveNodes` 회계 (1줄) — 눈을 먼저 고친다.
2. **§5-①** 네이티브 컨텍스트 (3줄) — 실측 기준 끊김의 90 % 이상이 여기서 사라진다.
3. ①을 넣은 채 **실기(사운드 카드 있는 기계)에서 재측정** — 이 문서의 «미측정» 칸(언더런, 청감)을 채운다.
4. **§5-②** `bakeStruck` 워커화 — 남은 0.2~1.3초 정지를 없앤다.
5. **§5-⑦** `duckSidechain` 예외 격리 (①을 하면 자동 해소, 그래도 방어는 남길 것).
6. **§5-④·⑥** 캐시 상한을 바이트 기준으로 · `sweep` 배치 상한 — ①·② 이후 다시 재보고 결정.
7. **§5-⑤** 는 ①을 못 할 때만.
8. AudioWorklet 은 §7-3 의 (A)(B)(C) 중 하나가 성립할 때까지 보류.
