# WebAssembly 도입 검토 — 그리고 대신 한 것

작성: 2026-08-15 · 대상: `src/audio/struck.js` · `src/audio/string.js`
선행: `docs/perf/01-오디오런타임.md`(병목 실측) — 이 문서는 그 §5-② 를 다른 방법으로 해결합니다.

---

## 0. 한 문단 요약

> **WASM 은 이 앱에 도움이 안 됩니다.** 소리의 대부분은 Web Audio 네이티브 노드가 내므로
> 이미 브라우저 안의 C++ 이고, JS 가 샘플을 도는 곳은 `bakeStruck()` · `ksInto()` 둘뿐입니다.
> 그 둘을 손으로 인코딩한 325바이트 WASM 모듈과 3자 비교한 결과,
> **WASM 은 최적화한 JS 보다 오히려 느렸습니다**(0.97x · 0.80x).
>
> 그런데 그 비교를 하려고 «WASM 이 쓸 수 있는 형태» 로 알고리즘을 바꾸는 과정에서
> **22.6배짜리 개선**이 나왔습니다. WASM 에는 `sin`/`exp` 명령이 아예 없어서 감쇠 사인을
> 복소 회전 재귀로 바꿔야 하는데, **그 재귀를 JS 에 그대로 두는 것만으로 이득의 전부가 나옵니다.**
>
> 적용 결과 피아노 한 음 굽기가 **509 → 20.2 ms**, 재생 중 최악 화면 정지가
> **825 → 69 ms** 가 됐습니다. 출력 파형 차이는 최대 **−149 dBFS** 입니다.

## 1. WASM 이 답이 아닌 이유

### 1-1. 이 앱에서 JS 가 샘플을 도는 곳은 두 군데뿐이다

`OscillatorNode` · `BiquadFilterNode` · `ConvolverNode` 는 이미 네이티브입니다.
WASM 으로 옮기면 **느려집니다.** `grep` 으로 확인한 결과 `AudioWorklet` · `ScriptProcessor` 는
쓰지 않고, 순수 JS DSP 루프는 `bakeStruck()`(struck.js) 과 `ksInto()`(string.js) 뿐입니다.

### 1-2. 3자 비교 **[실측]**

검증용으로 f64 산술만 쓰는 **325바이트 WASM 모듈을 손으로 바이너리 인코딩**했습니다
(툴체인이 없는 환경이고, 어차피 재는 대상이 루프 하나라 그편이 정확합니다).
`bake`(복소 회전)와 `ks`(KS 코어) 두 함수를 export 합니다.

**`bakeStruck` — piano C4, N=286,800 · Chrome 151**

| | 시간 | 배속 |
|---|---:|---:|
| A 현재 JS (`Math.exp`+`Math.sin`/샘플) | 263.7 ms | — |
| B 재귀 JS (초월함수 0회) | **12.9 ms** | **20.4x** |
| C 같은 재귀를 WASM 으로 | 13.3 ms | 19.8x |

C/B = **0.97x — WASM 이 더 느립니다.** Node v24 에서 4엔진 × 3음역 12조합 전부 같은 결론
(합계 1340 → 62.1(JS) → 64.3(WASM) ms).

**`ksInto` 코어 루프 — 12조합 합계**

| | 합계 | 배속 |
|---|---:|---:|
| A 현재 JS | 13.7 ms | — |
| B `%` 를 분기로 | 10.6 ms | 1.30x |
| C WASM | 13.2 ms | 1.04x |

C/B = **0.80x.** 직렬 IIR 이라 벡터화가 안 되고 힙 복사 비용만 붙습니다.

### 1-3. 왜 이런 결과가 나오나

* **WASM 에는 `sin`/`exp` 명령이 없습니다.** libm 을 링크하거나 재귀로 바꿔야 하는데,
  재귀로 바꾸는 순간 이득의 21배가 거기서 나옵니다. 남는 건 JIT 대 AOT 차이뿐이고
  V8 은 `Float32Array` 스칼라 루프를 이미 같은 기계어로 뽑습니다.
* 유일하게 WASM 이 더 줄 수 있는 건 SIMD128 로 파샬 2개를 병렬 처리하는 것인데,
  12.9 ms 에서 6 ms 아끼자고 툴체인을 들이는 셈입니다.

### 1-4. 덤으로 걸리는 것들

* **`file://` 더블클릭 흐름**(ARCHITECTURE.md 의 설계 전제) — `fetch('*.wasm')` 은
  `file://` 에서 CORS 로 막힙니다. base64 인라인하면 되지만 크기 +33% 에 빌드 단계가 생깁니다.
* **AudioWorklet + WASM** 조합은 `file://` 에서 아예 안 됩니다(`graph.js:429` 가 네이티브 노드만 쓴 이유).

> **결론 — WASM 은 도입하지 마십시오.** 같은 시도를 반복하지 않도록 이 문서를 남깁니다.

## 2. 대신 적용한 것

### 2-1. `bakeStruck` — 감쇠 사인을 복소 회전 재귀로 (`struck.js`)

원식은 샘플마다 `exp` 한 번 `sin` 한 번이었습니다. 파샬 48개(unison 3 × parts 16)에
버퍼 최대 6초라 초월함수 호출이 **1,400만 번**까지 갔습니다.

```js
z_i = amp·e^(−dec·i/SR)·e^(j(w·i+ph))     // 이 허수부가 정확히 원식
z_(i+1) = z_i · c,   c = e^(−dec/SR)·e^(jw)  // c 는 파샬당 한 번만
```

안쪽 루프에 곱셈 넷·덧셈 둘만 남습니다. ⚠ 실수부를 임시변수 없이 먼저 갱신하면
허수부가 새 실수부를 써서 회전이 깨집니다.

### 2-2. `ksInto` — 원형 인덱스의 `%` 를 분기로 (`string.js`)

`wp=(wp+1)%Di` → `if(++wp===Di) wp=0`. `dispWp` 도 같이. 이 루프의 유일한 나눗셈이었습니다.
**출력이 비트 단위로 동일합니다.**

## 3. 검증 **[실측]**

앱을 실제로 띄우고, `git show HEAD:` 로 뽑은 **수정 전 함수**와 앱이 로드한 **수정 후 함수**에
같은 난수 시드를 먹여 출력 버퍼를 샘플 단위로 비교했습니다(복사본이 아니라 앱이 도는 코드를 잽니다).

### 3-1. 파형 동일성

| | 조합 | 결과 |
|---|---|---|
| `ksRender` | 기타 8엔진 × 2음역 = 16 | **전부 비트 단위로 동일** (다른 샘플 0개) |
| `bakeStruck` | 4엔진 × 3음역 = 12 | 288,000 샘플 중 **최대 41개**가 다름, 최대 **−149 dBFS** |

`bakeStruck` 최악은 piano C2 의 3.0e−8(−149 dBFS)이고 marimba C6 은 비트 동일이었습니다.
Float32 양자화 한계가 −138 dB 이므로 **양자화보다 작은 차이**입니다. 누적 위상오차는
288k 샘플에서 상대 1e−13(배정밀도)이라 음정에 영향이 없습니다.

### 3-2. 굽기 단가 (Chrome 151, 앱 안에서 직접 측정)

## 4. 이것이 01번 문서에 미치는 영향

`01-오디오런타임.md` §5-② 는 `bakeStruck` 을 **Web Worker 로 빼는 것이 정답**이라고 했고,
그 근거는 «한 음 222~323 ms 는 스텝 예산 75 ms 의 3~4배» 였습니다.
지금 피아노 최악이 **20.2 ms** 이므로 **스텝 예산 안에 들어옵니다.**

> §5-② 의 워커화는 **필수에서 선택으로 내려갑니다.** 워커는 첫 음이 «옮겨 쓴 음정» 으로
> 한 번 울리는 대가가 있으므로(그 문서 §5-② 표), 20 ms 를 위해 그 대가를 치를 이유가 약합니다.
> 같은 문서 §5-④ 의 «캐시 상한이 빠듯해 재생 중 다시 굽는다» 도 재굽기 단가가 22배 싸져
> 압력이 크게 줄었습니다.

**§5-① (Tone.js SAC 래퍼) 는 그대로 1순위로 남습니다** — `onTick` p50 275 → 6.5 ms 는
여전히 이 앱에서 가장 큰 건입니다. 다만 커밋 `e3f54f6` 이 실측으로 확인했듯
`Tone.setContext()` 로는 안 됩니다(Transport 가 로드 시점 컨텍스트에 매여 «재생 중이라고
믿는데 소리가 안 나는» 상태가 됨). 그 커밋의 결론대로 **`connect` 호출 횟수를 줄이는**
방향이라야 합니다. **이번 작업에서는 건드리지 않았습니다.**
