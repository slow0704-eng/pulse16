## 1. 개요

| 항목 | 내용 |
|---|---|
| 시스템명 | PULSE·16 (MK XVI) |
| 한 줄 정의 | 브라우저에서 도는 **16스텝 리듬·화성 생성기** |
| 형태 | 서버 없는 정적 웹 애플리케이션 (SPA 아님 — 단일 문서) |

| 저장소 크기 | 약 2.9 MB (추적 파일 기준) |

### 1-1. 이 시스템이 하지 않는 것

- 사용자 데이터를 서버로 보내지 않습니다(전송 코드가 없습니다).
- 회원·과금·권한 개념이 없습니다.
- 오디오 파일을 내보내는 기능이 앱에 없습니다(계측 도구에는 WAV 렌더가 있습니다).
- 추적·분석 스크립트가 하나도 없습니다(확인함: WebSocket · EventSource · sendBeacon ·
  Service Worker · iframe · 애널리틱스 전부 0건).

| 구분 | 요구사항 |
|---|---|
| 브라우저 | Web Audio API 지원. 개발·계측 기준 Chromium 151 |

| 오디오 | 샘플레이트는 브라우저가 정함(계측 환경 48 kHz) |
| 빌드 도구 | **없음.** 트랜스파일·번들 단계가 존재하지 않습니다 |

### 2-1. 자동 재생 제약

브라우저는 사용자 제스처 없이 `AudioContext` 를 시작할 수 없습니다.
그래서 **첫 조작(`pointerdown` 또는 `keydown`)에서 그래프를 미리 짓습니다**.

> 유휴 시점(`requestIdleCallback`)에 짓던 판이 있었는데,
> 제스처 밖 컨텍스트 생성이라 «AudioContext was not allowed to start» 경고가
> 101개 쏟아졌습니다. 제스처 안으로 옮기니 이득은 같고 경고는 0이 됐습니다.

## 3. 소프트웨어 아키텍처

### 3-1. 왜 ES 모듈이 아닌가 — 의도된 결정

전부 평범한 `<script src>` (클래식 스크립트)입니다. 이유가 둘입니다.

1. **`file://` 로 열립니다.** ES 모듈은 CORS 로 막혀 로컬 서버가 필요합니다.
   더블클릭으로 여는 흐름이 이 제품의 설계 전제입니다.
2. 최상위 `const`/`let` 은 파일이 달라도 **전역 렉시컬 스코프를 공유**하므로,
   `import`/`export` 없이 파일을 나눌 수 있었습니다.

> **⚠ 그래서 `<script>` 순서가 곧 의존 순서입니다.** 순서를 바꾸면 깨집니다.
> 실제로 무언가를 *실행* 하는 파일은 `src/main.js` 하나뿐이고 나머지는 선언만 합니다.
>
> **⚠ `id` 와 같은 이름의 최상위 함수를 만들지 마십시오.** `id` 가 붙은 DOM 요소는
> 같은 이름의 암묵 전역을 만듭니다. 과거 `duck()` 이 `#duck` 슬라이더와 부딪혀
> `duckSidechain()` 으로 개명한 전례가 있습니다.

```

⑤  src/core/       dom · state · util          DOM 참조 · 전역 상태 · 노드 풀
```

## 4. 런타임 구조

### 4-1. 부팅 순서

```
페이지 로드
  └ main.js : 저장본 복원 또는 기본 프리셋 → UI 동기화 → rAF 미터 시작
       └ 첫 pointerdown/keydown  →  boot()
              · AudioContext 생성
              · 노드 495개 생성 · 노이즈/IR 65만 샘플 굽기
              · 실측 133~293 ms (중앙값 162)
```

### 4-2. 스케줄링 — 오디오 시계

자바스크립트 타이머는 수십 ms 흔들립니다. 그래서 **미래 시각을 예약**합니다.

```
onTick(t)   t = 이 스텝이 울려야 할 오디오 시각(현재가 아님)
            그 사이에 노드를 만들어 t 기준으로 파라미터를 예약
            메인 스레드가 늦어도 소리는 안 흔들림
```

- Tone.js 가 있으면 `Tone.Transport`, 없으면 내장 폴백(`fbLoop`)이 같은 일을 합니다.
- 화면 갱신(rAF)은 오디오와 분리 — 그림이 늦어도 소리는 정확합니다.
- 실측: rAF 미터 루프 0.06 ms/프레임 · DOM 갱신 0.11 ms/루프 (부담 0.36 %).

### 4-3. 보이스 생명주기와 노드 풀

스텝마다 노드를 새로 만들면 GC 가 주기적으로 멈추고, 그 멈춤이 곧 글리치입니다.

```
acqGain() / acqBQ()   풀에서 꺼냄
   → 연결 · 파라미터 예약
   → retire(node, 종류, 만료시각)   만료 후 풀로 반환
```

화면의 `nodes` 표시가 현재 살아 있는 노드 수입니다(정상 범위 실측 131~192).

> **⚠ 회수된 노드는 다른 보이스에 재배정됩니다.** 참조를 들고 있으면 엉뚱한
> 보이스를 죽입니다 — 오픈 하이햇 초크가 그 사례라, 만료 시 스스로 참조를 지웁니다.

### 4-4. 버퍼 캐시

현·타현 악기는 한 음을 통째로 구워 캐시합니다.

| 캐시 | 상한 | 대상 |
|---|---|---|
| `struckCache` | 48 | 피아노·하프시코드·비브라폰·마림바·글로켄 등 |
| `gtrBuf` | 24 | 기타·발현악기 35종 |
| `bassBuf` | 20 | 현 베이스 |
| `bufCache` | 무제한 | 외부 샘플(URL 키) |

## 5. 오디오 신호 경로

```
보이스(오실레이터 · 노이즈 · 구운 버퍼)
   │
   ├─ chan[트랙]  ─ 기타: 앰프체인 + Tone FX(페이저·와·코러스)
   │                 건반: 코러스(분산 딜레이)
   │      │
   │      ├─ panner[트랙] ─┬─ kick·bass·keys·keys2 → duckNode ─┐
   │      │                └─ 그 외 ──────────────────────────┤
   │      └─ send[트랙] → sendMono → convolver → revHP        │
   │                              → widener → revReturn ──────┤
   │                                                          ▼
   │                                                      mixBus
   │                                                         │
   │                                                     busTrim
   │            ┌───────────────┬──────────────────────────────┤
   │        (본선)          (Sub 병렬)              (Exciter 병렬)
   │   럼블컷 → 글루컴프   LP→LP→새추→게인      LP→프리→셰이퍼→HP→HP→LP→게인
   │            └───────────────┴──────────────────────────────┘
   │                                   ▼
   │                                sumBus
   │                 satIn → 셰이퍼 → satLP → satOut → masterGain
   │                                   │
   │                               리미터(limComp)
   │                                   │
   │                       트루피크 실링(tpClip, −3 dB 점근)
   │                                   ▼
   └──────────────────────────────  출력 + meterOut
```

### 5-1. 트루피크 실링이 리미터 뒤에 또 있는 이유 **[실측 근거]**

리미터는 어택 4 ms 라 1 ms 급 킥 클릭을 못 잡습니다. 실측에서 정상 상태 상한이
−3.53 dBFS 인데 트랜지언트가 그것을 3.5 dB 뚫고 나가 0 dBFS 를 넘었습니다.

- 문턱 아래는 **손대지 않습니다** — 라우드니스를 지키는 자리입니다.
- ⚠ `oversample` 은 반드시 `'none'`. 4x 재구성 필터의 깁스 오버슈트가
  첨두를 잡으라고 넣은 노드에서 첨두를 만듭니다.

## 6. 합성 엔진

### 6-1. 규모

| 트랙 | 엔진 수 | | 트랙 | 엔진 수 |
|---|---:|---|---|---:|
| kick | 9 | | perc | 19 |
| snare | 13 | | bass | 27 |
| clap | 9 | | keys | 43 |
| chat / ohat | 7 / 7 | | gtr | 35 |
| tom | 17 | | **합계** | **186** |

파라미터표: `KENG` 37 · `GTR` 35 · `BSTR` 11 · `BSYN` 8 · `STRUCK` 10.

### 6-2. 합성 방식 네 가지

| 방식 | 적용 | 원리 |
|---|---|---|
| **감산 합성** | 신스·오르간·관악·스트링 | 오실레이터 스택 → 24 dB/oct 로우패스. 음역 보정(key scaling)과 몸통 공명이 «신스» 와 «악기» 를 가름 |
| **Karplus-Strong** | 기타·발현악기 35 · 현 베이스 11 | 지연선 되먹임. β(뜯는 위치) 널 · 픽업 콤 · 복현 · 자와리 |
| **비조화 가산 합성** | 피아노·타현·말렛 | `f_n = n·f₀·√(1+B·n²)`. 실시간 불가라 **구워서 캐시** |
| **병렬 모달 뱅크** | 몸통 공명 (밴조 헤드·시타르 박·스틸팬) | 직렬 peaking 은 스스로 울지 않음 → 병렬 밴드패스 가중합 |

### 6-3. 파라미터 출처

- **STK**(Synthesis ToolKit, Cook·Scavone, MIT) — 타악기 10 · 말렛 6 · FM 건반 4
- **Mutable Instruments**(MIT) — 현 모델 분산·모달 공진
- 음향학 표준값 — 원형막 베셀 0점 모드비 · 자유단 막대 횡진동 모드비
- 라이선스 원문: `vendor/stk-LICENSE` · 환산식과 대조표: `docs/음색/01-STK차용.md`

> **GPL 계열(Surge XT · Vital)은 쓰지 않았습니다** — 전염성이라 저장소 전체를
> GPL 로 만듭니다.

## 7. 데이터 구조

### 7-1. 패턴 인코딩

| 종류 | 형식 | 의미 |
|---|---|---|
| 드럼 | 16자 문자열 | `X`=강세(2) · `x`=보통(1) · `-`=없음(0) |
| 베이스·기타 | 16자 문자열 | `0`~`7`=스케일 음도 · `-`=쉼표 |
| 건반 | 16자 문자열 | `0`~`7`=그 음도 3화음(비트마스크) · `a`~`h`=단음 · `-`=쉼 |

3화음은 인덱스 `r, r+2, r+4` 이고, 7 을 넘으면 7 을 빼서 **자리바꿈**으로 처리합니다.

> 펜타토닉(5음)에서는 `r,r+2,r+4` 가 근음·4도·b7 이 되어 3화음이 아니라
> **4도 쌓기 화음**이 됩니다. 힙합·록에서는 오히려 이쪽이 맞습니다 — 의도된 성질입니다.

### 7-2. 프리셋 스키마

```js
'프리셋명': {
  bpm, swing,
  kit  : {kick,snare,clap,chat,ohat,tom, [perc,keys,gtr,bass,keys2,gtr2,off]},
  tune : {kick,snare,tom,hat},
  bcfg : {eng,oct,semi,gate,glide,blend,drive,xover,tone,sub,exc,duck,root,scale},
  kick,snare,clap,chat,ohat,tom : 패턴 문자열,
  bass, keys, gtr               : 패턴 문자열,
  [perc, keys2, gtr2, prob, smp, cat, tone, gen]
}
```

### 7-3. 상태

| 대상 | 저장 위치 | 비고 |
|---|---|---|
| 패턴 뱅크 A~D | 메모리 (`banks[4]`) | 각각 12트랙 패턴 |
| 트랙 상태 | 메모리 (`eng`·`lvl`·`mute`·`src`·`probT`) | |
| 노브 값 | DOM (`input[type=range]`) | 단일 진실 원천 |
| 세션 저장 | `localStorage['pulse16.mk16.v1']` | 약 4000자 |

Undo/Redo 는 메모리 스택입니다(저장 대상 아님).

|---|---|
| 재생·전 UI·폰트·`HAS_TONE` | **정상** |
| 외부 샘플 엔진 | 사용 불가 (설계상 정상) |

## 9. 비기능 특성 **[실측]**

### 9-1. 성능

| 지표 | 값 |
|---|---|
| 첫 방문 요청 / 오리진 | 55 요청 / **1 오리진** |
| FCP (로컬, 무지연) | 248 ms |
| `boot()` 메인스레드 점유 | 133~293 ms (중앙값 162) |
| 피아노 한 음 굽기 | **20.2 ms** (개선 전 509 ms) |
| 재생 중 최악 화면 정지 | **62~69 ms** (개선 전 765~825 ms) |
| rAF 간격 p50 | 16.7 ms (60 fps) |
| 메모리 | 180초 재생 중 진동, 단조 증가 없음 = **누수 없음** |

### 9-2. 알려진 병목 **[미해결]**

**Tone.js 14.7.77 의 `rawContext` 가 네이티브 `AudioContext` 가 아니라
standardized-audio-context 래퍼입니다.** 앱의 모든 `createX`·`connect`·
`setValueAtTime` 이 그 래퍼를 지납니다.

- 실측 단가 차이 12~870배. `connect()` 한 줄이 12 ms(네이티브 0.0095 ms).
- 최악 조건 `onTick` 중앙값 275 ms (스텝 간격 75 ms).

> **⚠ `Tone.setContext(new Tone.Context(native))` 로 고치려던 시도는 실패했고
> 되돌렸습니다**(커밋 `e3f54f6`). `Tone.Transport` 가 라이브러리 로드 시점
> 컨텍스트에 매여 있어 컨텍스트를 갈면 `state` 가 `'stopped'` 에 머뭅니다 —
> «앱은 재생 중이라 믿는데 소리가 하나도 안 나는» 최악의 상태가 됩니다.
> 고칠 길은 컨텍스트 교체가 아니라 **`connect` 호출 횟수 줄이기**입니다.

### 9-3. WebAssembly 검토 결과 — **도입하지 않음**

JS 가 샘플을 도는 곳은 `bakeStruck` · `ksInto` 둘뿐이라, 손으로 인코딩한
325바이트 WASM 모듈과 3자 비교했습니다. **WASM 이 더 느렸습니다**
(최적화 JS 대비 0.97x · 0.80x). WASM 에는 `sin`/`exp` 명령이 없어 어차피
복소 회전 재귀를 써야 하고, 그 재귀를 JS 에 두는 것만으로 이득이 다 납니다.
근거: `docs/perf/03-웹어셈블리검토.md`.

## 11. 변경 시 주의사항

1. **로드 순서 = 의존 순서.** 새 파일은 자기 의존 대상 뒤에 넣으십시오.
2. **`id` 와 같은 이름의 최상위 함수 금지.**
3. **외부 오리진을 다시 들이지 마십시오.** 지금 0개입니다.
4. **`tools/` 하네스에 앱 코드를 복사하지 마십시오.** 복사본은 조용히 거짓말합니다.
5. **레벨을 바꾸면 렌더해서 재십시오.** 노이즈 여기 타악기는 한 방 측정의
   회차 편차가 최대 8.4 dB 입니다 — 10회 평균이 필요합니다.
6. **핑크 노이즈로 바꾸면 amp 보정이 따라와야 합니다.** 화이트보다 RMS 가
   9~15 dB 낮습니다(실제로 한 번 밟은 함정입니다).
